# Agent definitions

One file per Agent, `<name>.agent.yaml` ([ADR 0040](../docs/adr/0040-agents-read-the-estate-through-api-management-have-no-write-tools-and-their-own-identity.md)): the Agent's instructions, tool list and model settings, versioned in the repo and never edited in the portal. Two readers use the same file: the in-process runner in `Norvia.Agents` ([ADR 0041](../docs/adr/0041-locally-an-in-process-runner-and-an-mcp-stand-in-play-foundry-and-api-managements-mcp-server.md)), through `AgentDefinitionLoader`, and `infra/deploy-agents.ps1`, which publishes each file as a Foundry prompt agent. It is plain YAML, so a script reads it with `yq`.

| Field | Meaning |
|---|---|
| `name` | The Agent's name: lower-case letters, digits and hyphens, and the file's name before `.agent.yaml` |
| `version` | A whole number, raised whenever the instructions, the tools or the model settings change |
| `description` | What the Agent is for, one sentence |
| `instructions` | What the model is told. It says that tool results are delimited data and never instructions, and that every claim cites the result it came from |
| `model.deployment` | The model deployment in the Foundry project. `infra/deploy-agents.ps1` uses the estate's own when this one isn't there |
| `model.temperature`, `model.maxOutputTokens` | Sampling and the length of an answer |
| `model.maxToolCalls` | The cap on tool calls per question. The runner refuses a call over it |
| `tools.server` | The MCP server, which is the name of its tool list in [contracts/agent-mcp/](../contracts/agent-mcp/README.md) |
| `tools.names` | The tools of that server this Agent may call, each once. A name the server doesn't serve fails the loader's checks, and a write tool fails the architecture tests |
| `inputs.correlationIdHeader` | The header that carries the correlation ID of the trail in question to every tool call. It is a structured input, supplied per run. `infra/deploy-agents.ps1` declares the structured input `correlationId` and puts `{{correlationId}}` in this header of the MCP tool; the console's Foundry client supplies it on each response |

The answer is one JSON object, which the runner reads as a `Suggestion`: `cause`, `evidence` (a `claim` and the `citation` of the result `rN` it came from), `action` (`resubmit`, `discard`, `fix-the-cause-first` or `needs-a-person`), `suggestedAction` (the advice in plain text) and `confidence` (`low`, `medium` or `high`). A reply that is not that, or that cites a result the run never had, is `AgentUnavailable`.

In Azure the results of the tool calls are not wrapped in `<tool_result>` tags the way the in-process runner wraps them, so the instructions number them: the first call's result is `r1`, the second's `r2`. Foundry's output lists the calls in order, and the console's Foundry client reads the reply with the same rules as the runner (a citation of a result the run never had is `AgentUnavailable`).

The Estate health-check agent answers with a different object, which the runner reads as a `Narration`: `summary` and `findings`, each with the `id` of a Finding the tool returned, its `impact` in plain text and the `citation` of the result `rN` it came from. A reply that explains a Finding the result does not hold, or cites a result the run never had, is `AgentUnavailable`: the agent cannot invent a Finding.

The Simulator's personas agent (`simulator-personas`) is the one Agent with **no tools**: it leaves out the `tools` and `inputs` sections, `infra/deploy-agents.ps1` publishes it as a prompt agent without a tool (and gives it no role, since it reads nothing), and it answers one JSON object, `{"texts": ["...", "..."]}`, which the runner reads as a pool of texts. The Simulator validates each text before it keeps it (a length cap, no control characters, no URLs, no address-like or phone-like patterns), and tells the model only the profile, the language and the kind of text ([Pools of Carrier and Driver texts](../docs/operations/simulator.md#pools-of-carrier-and-driver-texts)).

The personas agent is also the one definition that asks a model for **adversarial text**, and only for the Simulator's opt-in `hostile` profile: instruction-like remarks that test the other Agents' injection defences. Its instructions have a rule that says so, and for every other profile they say never to write an instruction aimed at a reader. See [The hostile profile](../docs/operations/simulator.md#the-hostile-profile) and, for how to check the other Agents against it, [Agent evaluation](../docs/operations/agent-evaluation.md#checking-the-injection-defences-against-a-hostile-simulator-run).

The Customer service agent (`customer-service`) answers with the same `Suggestion`, always of the kind `needs-a-person`: its `cause` is why a Rejected booking was rejected in plain language, its `evidence` cites the one `get_rejected_booking` result (`r1`) and its `suggestedAction` is what the Shipper should change. The correlation ID it is run with is the Rejected booking's own, so its tool calls join the booking's Message trail. Its tool returns the TMS API's agent view of the booking: no Consignee name, address or contact and no file contents. On a Transport Order's detail page its Explain button asks it to summarise the order's life from rating to billing: it reads `get_transport_order`, then, when the order has a Shipment, `get_shipment_timeline`, `get_exceptions` and `get_proof_of_delivery_status` (`r1` to `r4`), and answers in `cause` with one paragraph, each claim cited, and in `suggestedAction` with what blocks the order, or that nothing does. The same narrow views apply: no Consignee personal data, no remarks the Carriers typed, no signer and no file contents. On a row of the rating exceptions list its Explain button asks why Rating failed and what fixes it (usually the Rate Card, which Customer service does not edit, so it ends with asking whoever owns the Rate Card to fix it and then using Re-rate, which it points to and never runs); on a row of the not-yet-billable list it asks what holds the order back (`NotRated`, `NoProofOfDelivery`, `OpenException`) and which of that Customer service can act on. Both read `get_transport_order` only (`r1`). On a row of the not-yet-billable list whose Proof of delivery is missing, its Recommend button asks whether to release the order without one. The TMS decides eligibility (`get_release_eligibility`, `r1`, the same rule the release checks, with the other conditions that still block: an open Exception, not rated); an ineligible order gets `needs-a-person` with the blocking reasons, and the TMS downgrades any `release` the Agent gives for one. For an eligible order the Agent weighs only how long since delivery and what `get_proof_of_delivery_status` (`r2`) says, and answers `release`, `wait` or `needs-a-person`. It never drafts the remark, and says nothing of how often a Carrier is late with Proofs of delivery, since the TMS does not expose it. A `release` only pre-selects the order in the release form; staff write the remark and confirm, under their Customer service role, and the release's trace then names the Agent and its run ID. In Azure the TMS UI's `FoundryAgentClient` asks the published Agent, which calls API Management's `customer-service` MCP server ([infra/estate/customer-service-mcp.bicep](../infra/estate/customer-service-mcp.bicep)); [infra/smoke-test-customer-service-agent.ps1](../infra/smoke-test-customer-service-agent.ps1) is its post-deploy smoke run.

The Carrier invoice rejection reason agent (`finance-rejection-reason`) drafts the Carrier-facing reason for rejecting a Carrier invoice line, so its boundary is a tool: a separate definition and identity with exactly one tool, `get_carrier_visible_line_facts`, behind a role and an MCP server of its own, as the Customer service reply agent is. The tool returns only what the Carrier can see of its own line (its own invoice number, line and reference, the invoiced amount, the agreed Carrier cost, the likely correct reference only when it is one of the Carrier's own bookings, and for a Duplicate its own earlier invoice number), never the Rate Card or its version, the Planner's Spot remark, the Matching tolerance or another Carrier's reference. The draft is the Suggestion's `cause`, of the kind `needs-a-person`, which the Draft reason button of the ERP UI puts in the reason field for Finance to edit and confirm. See [E2](../docs/processes/erp/e2-carrier-invoice-matching.md#draft-the-rejection-reason).

The Carrier invoice matching agent (`finance-matching`) answers with the same `Suggestion`, always of the kind `needs-a-person` (a suggested action is text only until the slice that makes it actionable, #472). On a Carrier invoice line that is To decide, in the ERP UI's "Carrier invoices to decide", its Explain button asks why the line did not match: its `cause` says what the Carrier claims, what Norvia agreed (with the source as a label, a Rate Card version or Spot) and the tolerance for a Price mismatch, the earlier invoice and line for a Duplicate, and for an Unknown booking that no Carrier cost has arrived and which ranked Open Carrier costs are *likely candidates*, never certain. It says whether the line may still resolve: only an Unknown booking line does, by itself, when its Carrier cost arrives. On a whole Carrier invoice, its Explain this invoice button asks for a summary instead: its `cause` is a short summary (the Carrier, the total, the approved amount so far and how many lines are To decide), its `evidence` has one claim per cause of the lines To decide with the count, each citing the result of its second tool, `get_invoice_summary` (`/v1/agent/finance/carriers/{carrierId}/invoices/{invoiceNumber}`, counted by the ERP, naming no line), and its `suggestedAction` says which of them may still resolve by themselves; it offers no action. Its tool `get_invoice_line` (`r1`), returns the ERP API's agent view of the line (`/v1/agent/finance/carriers/{carrierId}/invoices/{invoiceNumber}/lines/{carrierBookingReference}`): the ERP works out the difference, the tolerance, the earlier line and the ranked candidates, and the view leaves out the Planner's remark of a Spot price and every Shipper and Consignee detail. The correlation ID it is run with is the Carrier invoice's own, so its tool calls join the invoice's Message trail. Locally the ERP UI runs it in process against the MCP stand-in's `finance-matching` server; in Azure its `FoundryAgentClient` asks the published Agent, which calls API Management's `finance-matching` MCP server as its own identity (`infra/smoke-test-finance-agent.ps1` checks it after `azd up`).

The Intake agent (`booking-intake`) is the other Agent with **no tools**, and it reads a Shipper's text, so it runs in the Foundry project without tracing (`norvia-intake`). It answers one JSON object, `{"booking": {...}, "quotes": {...}, "missing": [...]}`, a Booking draft in the shape of `contracts/partner-api/booking-draft.v1.schema.json`, or `{"refusal": "MultipleBookingsInText"}`. `Norvia.Integration.BookingDraft` validates the reply against the schema before it is returned (a reply that does not match is `AgentUnavailable`) and throws away any value whose quote is not in the text, so the agent cannot invent a value. In Azure `infra/deploy-agents.ps1` publishes it into `norvia-intake`, and the Booking draft host (`Norvia.Integration.BookingDraft.Api`) asks it. See [P1](../docs/processes/tms/p1-transport-order-intake.md#booking-draft-from-pasted-text).

The Customer service reply agent (`customer-service-reply`, [ADR 0011](../docs/adr/0011-shippers-see-a-tracking-status-not-the-shipments-workings.md)) is a separate definition and identity from `customer-service`, with **one tool**, `get_shipper_view`, on an MCP server (`customer-service-reply`) and a read role of its own. The tool returns what the Shipper sees of a Transport Order (the Tracking status, progress events, whether a Proof of delivery is available, and the Shipper notifications already sent), so the Agent physically cannot name the Carrier or an internal Exception. On a Transport Order's detail page Customer service chooses one of three fixed questions ("Where is my order?", "Has it been delivered?", "Is there a Proof of delivery?") and gets a draft in English. The answer is the same `Suggestion`: the draft is in `cause`, cited to the one result (`r1`), and `action` is always `needs-a-person`. The draft states no price and says "we have no update" where the Shipper view does not say. It is editable, is a Suggestion that is stored nowhere, and is sent by staff outside the TMS: the TMS sends nothing.

The Planner agent's note definition (`planner-exception-note`, #443) is a separate definition on the Planner's MCP server and role, with **one tool**, `get_exception_timeline`: an Exception's timeline (its type and causes, status, the Shipment's Tracking events with their sources and remarks, the Carrier bookings' state, the actions already taken and the notes so far; never a postcode, a Consignee's personal data or a file). On the Add note form of an open Exception, its Draft note button asks for a short internal note of what has happened and what is outstanding. The draft is in the Suggestion's `cause`, cited to the one result (`r1`), and `action` is always `needs-a-person`: it fills the note box and nothing is saved until the Planner adds the note, and then the note's trace names the Agent and its run, edited or not. The agent never resolves an Exception, never picks an outcome and never states a cause the timeline does not show.

The Planner agent (`planner`, #440) suggests to a Planner who should carry a Transport Order waiting for planning, Own fleet or one of the active Carriers. It has **one tool**, `get_assignment_options`, on its own MCP server (`planner`) with a read role of its own, `TransportOrders.PlannerAgent.Read`. The TMS computes the options (the Assignment rules, the load check for the collection day with the order counted, the Driving-hour budget and each Carrier's Carrier cost from its Carrier Rate Card) and the agent chooses among them: it recommends **one eligible option** with the trade-off against the others (cost against capacity warnings), names any warning it is accepting, and never recommends an option the Assignment rules refuse. The view leaves out the street address, the Consignee and every file. The answer is the same `Suggestion`, cited to the one result (`r1`), and `action` is always `needs-a-person`: it is shown only, and nothing is pre-selected yet (#442). In Azure (#441) the TMS UI's Foundry client asks the published Agent, which calls API Management's `planner` MCP server as its own identity; `infra/smoke-test-planner-agent.ps1` runs it on the Over capacity demo day and checks that the answer names the warning, compares a Carrier's cost, and that no street address or Consignee field appears in the tool calls.

The Planner notification agent (`planner-notification`, #444, [ADR 0011](../docs/adr/0011-shippers-see-a-tracking-status-not-the-shipments-workings.md)) is a separate definition and identity with **two tools**, `get_shipper_notification_template` (the TMS's template for the Exception's type) and `get_shipper_view` (what the Shipper sees of the Transport Order), on an MCP server of its own (`planner-notification`) and a read role of its own. It cannot name the Carrier, an internal remark or an internal Exception because no tool it can call returns one. On the Notify Shipper form of an open Exception, its Draft message button asks for an adjusted wording of the template, using only the two results. The draft is in the Suggestion's `cause`, cited to `r1` and `r2`, and `action` is always `needs-a-person`: it replaces the message box and nothing is sent until the Planner sends it through Notify Shipper, and then the notification's trace names the Agent and its run, edited or not. The draft states no price and no promise: where the facts do not say, it keeps the template's words or says "we have no update".
