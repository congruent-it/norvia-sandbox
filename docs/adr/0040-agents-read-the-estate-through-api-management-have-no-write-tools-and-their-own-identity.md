# Agents read the estate through API Management, have no write tools and have their own identity

**Status: Accepted.** The first two slices of the Integration operations agent work end to end (#379 locally, #380 in Azure), as #369 says.

Norvia's staff get **Agents**, built on Microsoft Foundry (Foundry Agent Service): an Agent reads the estate and answers a person, and the person decides. This ADR says what an Agent is, what it may touch and who stays in charge. How it runs on a developer's machine is [ADR 0041](0041-locally-an-in-process-runner-and-an-mcp-stand-in-play-foundry-and-api-managements-mcp-server.md).

- **One tool door.** An Agent reaches an estate application only through an MCP server that API Management exposes over the application's REST API: each allowed operation is one tool. So [ADR 0001](0001-realistic-applications-integrated-only-through-ais.md) and [ADR 0003](0003-http-in-events-out.md) hold: a read goes from API Management straight to the application's API, and a tool call is a hop on a Message trail. Foundry never connects to an application, a database or Service Bus. The Developer tier supports MCP servers ([ADR 0021](0021-api-management-runs-on-the-developer-tier.md)); only tools are supported, not MCP resources or prompts, and response payload logging must be off at the global scope.
- **Reads of Azure itself use the same door.** Resource Graph, Cost Management, run history and dead-letter queues are read by a read-only API that an application owns (the Integration console, or a health-check API) under its own managed identity, and exposed through API Management MCP. The Agent holds only a role to call that API, never an Azure role.
- **No write tools.** An Agent's tool list contains read operations only. What it proposes is a **Suggestion**, shown in the host application's UI. The person confirms, and the application makes the command under the person's own role and token, as it does today, so every Assignment rule, refusal and Idempotency-Key still applies. A write tool on any Agent needs its own ADR.
- **A Suggestion is not a domain concept** ([ADR 0002](0002-one-system-of-record-per-concept.md)). It lives in the host UI for the session and is stored nowhere. When the person acts on one, the command's trace carries the Agent's name and the run ID. An ignored Suggestion is not recorded, and the Agent is never told whether a Suggestion was accepted.
- **The system computes the facts and the Agent chooses.** Where a rule decides what is allowed (Assignment rules, release eligibility, the actions a Carrier invoice line allows), the owning application computes it in a read query, using the code its command runs. The Agent explains and picks among what is allowed, and cannot recommend what the rules refuse.
- **Own identity, read roles, once published.** Foundry creates an Agent's Entra agent identity when the Agent is **published**, and gives it a new identity on every publish. Unpublished agents in a project share the project's identity. So every estate publishes its Agents, the project's shared identity holds **no roles** (an unpublished agent can call nothing), and a script gives each new identity the one read role of the narrow API view it calls, after every publish. The identities and roles are listed in the [identity and access matrix](../architecture/identity-and-access.md). An Agent that writes Carrier-facing or Shipper-facing text is a separate Agent with a separate identity and a single tool, so the boundary is a tool and not an instruction.
- **A narrower view, not the full read model.** An Agent's operations return what it needs and nothing else: statuses, codes, times, numbers and business names. Consignee names, addresses and contacts, and file contents, are excluded by default, from an allowlist of fields, so a new field is excluded until someone adds it. A tool that returns personal data is named in its epic and justified. The one Agent that receives personal data as *input* is the Intake agent, which reads a Shipper's email.
- **Prompt agents, definitions in the repo.** An Agent's instructions, tool list and model settings are versioned files in our own YAML format, read by both runners and never edited in the portal. Hosted agents are used only when an epic shows it needs custom code. Bicep owns the Foundry account, project, model deployment and tracing connection. A deploy script, run in the `azd` postdeploy hook like the Logic App deploy scripts, publishes each definition and creates the agent-identity MCP connections if Bicep cannot (its connection schema has no agent-identity type), and a second script assigns the roles. The applications own the Agents' code and definitions ([ADR 0004](0004-bicep-owns-the-estate-aspire-owns-the-apps.md)).
- **Each host application owns its `IAgentClient` port** in its Application layer. Infrastructure implements it with the Foundry client in Azure ([ADR 0041](0041-locally-an-in-process-runner-and-an-mcp-stand-in-play-foundry-and-api-managements-mcp-server.md) says what plays it locally). A shared library, `Norvia.Agents`, holds the definition loader, the runner, the scripted fake, the shared Suggestion result and the tool-list contract. An architecture test allows only Infrastructure projects to reference the Foundry SDK.
- **Tracking.** The API Management policy records the Agent's identity (`azp`) and the tool name as tracking keys on each tool call ([coding guidelines §7](../coding-guidelines.md#tracking-contract)). The host application records the Agent run as a span with its run ID and the Foundry conversation ID, linked to its tool calls by the correlation ID it passes down: Foundry sends it as a header on each tool call, declared as a structured input in the Agent's definition and supplied per run. Foundry traces go to Application Insights with content recording off. If server-side tracing cannot be set not to record prompt content, the Intake agent runs in its own Foundry project with no tracing connection.
- **Untrusted text.** Carrier remarks, Shipper free text, message bodies, Exception notes and resource tags reach the model through tool results, so they are data, never instructions. Instructions say so and results are delimited. Foundry content filters and prompt shields are on. An Agent's output is plain text or sanitised Markdown, never HTML, with links only to the repo's own application routes. Every claim cites the tool result it came from. With no write tools, the worst a successful injection can do is mislead, and each epic carries injection cases in its evaluation set.
- **Personal data.** Foundry is in an EU region and the model is a `DataZoneStandard` deployment, so processing stays in the EU Data Boundary (`GlobalStandard` is not used). The Agent Service is stateful: it keeps conversations and responses until they are deleted. So the host application deletes the run's conversation and responses when the run ends, a nightly sweeper deletes any older than a day (far inside `integrationRetentionDays`, [ADR 0017](0017-the-integration-console-reads-the-estates-telemetry-and-stores-nothing.md)), and the Intake agent deletes before it returns its draft. The Responses API has a `store: false` option, which the clients set on every call and which means no conversation is created either (the spike of #500, [operations/foundry.md](../operations/foundry.md#spike-3-a-store-nothing-option)); it is not a guarantee that the service stores nothing, so the deletes stay and the sweeper is the safety net. Agents keep no memory between runs, and no customer data is used for training.
- **Failure.** An Agent is never on a critical path. When Foundry or the model is down the host UI shows "Assistant unavailable" and everything else works. There is a short timeout and no automatic retry. The failure codes are `AgentUnavailable` and `AgentToolRefused`, and the run is a span marked `Failed`.
- **Guards.** `Agents:Enabled` is off unless the estate turns it on (as `Simulator:Enabled`, [ADR 0039](0039-the-simulator-books-only-through-the-estates-real-doors.md)). One small shared model deployment per estate. A cap on tool calls per question and a request-rate limit per Agent in API Management. Every Foundry resource carries a cost tag, so the spend is visible to the as-found cost story.
- **As-found toggles for Agents.** The estate can be made as-found in these ways, and a health check should find them: no content filter or prompt shield, an Agent identity with a role wider than read, no per-Agent cap or rate limit, no cost tag, `Agents:Enabled` on in a public Demo UI, an unlimited model quota, no conversation sweeper (`noConversationSweeper`, built in #500). #377 builds the others; the Estate health check finds them.
- **Evaluation.** CI runs only the scripted fake: wiring, authentication, tool lists, no write tool, drift. Quality evaluations run in Azure on demand and before a release, against evaluation sets kept in the repo and seeded from the Simulator and the as-found faults, so the known answer is the toggle that was on. They never gate a merge.

## Considered Options

- **Agents with write tools and an approval step in the agent:** faster for a person, but an Agent that can write has to be trusted to ask first, and a prompt injection could skip it. Without write tools the approval is a property of the design, not of the model's behaviour.
- **Foundry connected straight to the applications or to Azure (the Azure MCP server):** no API Management work, but nothing is on a Message trail, role scoping is per application, and the estate's single door and rate limiting are bypassed.
- **One shared identity for all Agents:** fewer role assignments, but a single role would be the union of every Agent's tools, and one Agent's compromise reaches them all.
- **Suggestions stored as a domain concept** (a table in each application): an audit of what was proposed, but a new system of record in every application for text that is only advice. The history is the telemetry, which the Integration console already reads.
- **Agents that call the Shipper-facing tracking API on a Shipper's behalf:** the Shipper's token would have to pass through the Agent. That is a different, higher risk (an external user, free text, a made-up delivery date) and needs its own ADR before it is built (#428).

## Consequences

- Every application an Agent reads gets an agent view: a narrower, read-only endpoint group, its own role and its own MCP server behind an API Management API. The TMS API has no API Management front today, so the first Agent for the TMS adds one.
- A person who cannot reach an Agent loses nothing. A demo can still show every step of every process without one.
- Agents add costs (a model deployment, API Management calls, Foundry traces). The guards, the cost tag and the off-by-default setting keep them visible.
- The Intake agent's input holds personal data. It has its own controls (a stateless operation, no stored or logged text, EU region), named in its epic.
- Every tool list exists in two places: the Bicep for API Management and the local stand-in ([ADR 0041](0041-locally-an-in-process-runner-and-an-mcp-stand-in-play-foundry-and-api-managements-mcp-server.md)). A test keeps them equal.
- An Agent whose boundary is a tool needs its own definition and identity. That is more pieces for the Notify Shipper draft, the reply draft and the rejection reason, and it is the price of a boundary the model cannot cross.
