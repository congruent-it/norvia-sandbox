# The Simulator signs in with Easy Auth, reaches the estate as its own identity and plays the Personas and Drivers through Entra client apps

The Simulator ([ADR 0039](0039-the-simulator-books-only-through-the-estates-real-doors.md)) acts only through the estate's real doors, locally and in Azure. Locally it signs every token itself. In Azure the same code gets its tokens from Entra, and the presenter signs in with Entra.

- **The presenter signs in with Easy Auth and a role.** The Simulator sits behind Container Apps' Easy Auth, like the Integration console ([ADR 0026](0026-the-integration-console-signs-operators-in-with-easy-auth-and-checks-their-app-role.md)), and signs in to an app registration of its own, *Norvia Simulator*, with the app roles `Simulator.Run` (configure, start and cancel runs, clear the history) and `Simulator.Read` (see runs and their logs). The registration needs a role assigned (`appRoleAssignmentRequired`), so someone without one is refused by Entra before they reach the Simulator; someone who signs in with only `Simulator.Read` is refused by the Simulator on the pages that need `Simulator.Run`. The presenter holds both. The Simulator reads the user and their roles from the `X-MS-CLIENT-PRINCIPAL` header, which Container Apps doesn't let a request from outside set.
- **It reaches the estate as its own managed identity.** The estate owns a user-assigned identity for the Simulator. It holds the TMS API's `TransportOrders.Manage` role, as the TMS UI's identity does, for the Planner's actions (assignments, releases, Trips and Exceptions), and the Simulator asks Entra for the Planner's token with it.
- **Each Persona and each Driver is a client app that trusts that identity.** A Persona's token for the Norvia Partner API comes from the Persona's own client app, which gains a second federated credential that trusts the Simulator's identity beside the Partner portal's ([ADR 0005](0005-partner-identity-comes-from-the-token.md)); the Persona's roles are the ones it already holds, so the Simulator can do for a Persona exactly what the Partner portal can. A Driver's token for the Driver app API comes from a client app for that Driver, one per active Driver of the seed file, which holds the Driver ID as its **one app role on the Driver app API** and trusts the Simulator's identity. The Driver app takes the Driver ID from that role, as it does from a Driver's own sign-in ([ADR 0037](0037-drivers-sign-in-to-the-driver-app-with-entra-and-the-driver-id-is-their-app-role.md)). There are no client secrets anywhere. The Simulator holds one identity; what each Persona and Driver may do is what the estate granted their client app.
- **The subscription keys come from Key Vault.** The Simulator's identity reads the Personas' subscription keys from the Partner portal's vault (Key Vault Secrets User), with the Partner portal's.
- **The estate switches it on and caps it.** `Simulator:Enabled` is a parameter of the estate (`simulatorEnabled`, on by default), as are the caps (`simulatorMaxOrdersPerRun`, 200, and `simulatorMaxConcurrentRequests`, 4), lower than the Simulator's own because API Management is on the Developer tier ([ADR 0021](0021-api-management-runs-on-the-developer-tier.md)) and the Logic Apps bill by action. Switched off, the Simulator answers every request but its health checks with 404.
- **The same code, a different token source.** Each of the Simulator's three token sources (Personas, Planner, Drivers) has a local implementation that signs the token and an Entra one, and configuration picks exactly one: `Entra` or `LocalTokens`, validated at startup. The sign-in is the same: a local operator in Development, Easy Auth anywhere else. The Simulator **refuses to start with local-operator settings outside Development**, as the console does, because those settings would let anyone in with the roles they name.

## Considered Options

- **One client app for all Drivers, with a role per Driver:** a token would hold every role, and the Driver app takes the Driver ID from a token with exactly one. A client app per Driver keeps the Driver app's rule and its API as they are.
- **The Drivers' Entra test users with a password:** the users exist for the Driver app's sign-in ([ADR 0037](0037-drivers-sign-in-to-the-driver-app-with-entra-and-the-driver-id-is-their-app-role.md)), but a password sign-in for an app holds a shared secret, doesn't work for a tenant that requires multi-factor authentication, and gives a token for the Driver app's registration, not the API's.
- **A client secret or a certificate for the Simulator's client apps:** something to rotate, where a federated credential on a managed identity needs nothing.
- **A role on the TMS API of its own for the Simulator:** more precise than sharing the manage role with the TMS UI, but the Planner's actions are the TMS UI's actions, which the TMS API guards with the manage role ([identity and access](../architecture/identity-and-access.md)). The Simulator is the second principal that holds it.

## Consequences

- The Simulator's identity can do whatever the TMS UI's can in the TMS, and everything every Persona and Driver client app can do. It is a demo tool: the estate can switch it off, and `Simulator.Run` is held by the presenter only. Someone else who runs it needs the role on *Norvia Simulator* in Entra ID.
- Entra needs the Simulator's callback, which exists only once Aspire has deployed it. The postdeploy hook ([infra/register-sign-in-callbacks.ps1](../../infra/register-sign-in-callbacks.ps1)) adds it and keeps it in the azd environment as `ESTATE_SIMULATOR_REDIRECT_URIS`.
- The estate grows a client app, a service principal, a federated credential and a role assignment for each seeded Driver. A new Driver in the seed file gets them on the next estate deployment.
- Its migrations are a Container Apps job like the other databases', started by the postdeploy hook.
- The Entra token sources are not unit tested against Entra. Their wiring and the choice between Entra and local tokens are, and the post-deploy smoke run ([infra/smoke-test-simulator.ps1](../../infra/smoke-test-simulator.ps1)) shows that the tokens work.
