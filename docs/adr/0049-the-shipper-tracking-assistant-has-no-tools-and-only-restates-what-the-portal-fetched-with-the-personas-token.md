# The Shipper tracking assistant has no tools and only restates what the Partner portal fetched with the Persona's token

**Status: Proposed.** [ADR 0040](0040-agents-read-the-estate-through-api-management-have-no-write-tools-and-their-own-identity.md) left Shipper-facing Agents out and said they need their own ADR (#428). This is it. It decides the **Shipper tracking assistant**: a conversational layer over the Partner portal's tracking screen (P8), where a Persona asks about its own Transport Orders. Its slices (#878, #879, #880) are built on this ADR.

A Shipper-facing Agent is a different class of risk from the staff-side ones: the asker is an external user, the question is free text, and a made-up delivery date is a promise Norvia did not make. Everything else ADR 0040 decided still holds and is not reopened here: EU region and a `DataZoneStandard` model, `store: false`, no memory between runs, "Assistant unavailable" when Foundry is down, `Agents:Enabled` off by default, untrusted text is data, and injection cases in the evaluation set. [ADR 0011](0011-shippers-see-a-tracking-status-not-the-shipments-workings.md) decides what a Shipper may see, and [ADR 0005](0005-partner-identity-comes-from-the-token.md) says identity comes from the token.

- **Whose authority: the Persona's, used by the portal and never by the model.** When a Persona asks a question, the Partner portal calls the Norvia Partner API itself, with the Persona's own token and subscription key (the ones the tracking screen already uses), and gives the response to the Agent as input. The Agent has **no tool, no MCP connection and no credential**. So the TMS decides what the Persona may see, as it does for the screen, and the model cannot ask for another Shipper's order: there is nothing for it to ask with. A cross-Shipper answer is impossible by construction, not by instruction. The Persona's token never reaches Foundry.
- **What the portal fetches.** The portal chooses the data, not the model: the Transport Order open on the screen, if any, in full (the detail operation), and the first page of the Persona's list (the list operation, at most 20 orders, newest collection date first). If the Shipper's question names a Shipper reference or a number that is in neither, the portal may call `find` once for it before the run. Anything else is not in the input, and the answer says so. The portal passes the responses unchanged, as the API returned them: the TMS already made the projection of ADR 0011, so the Carrier, Exceptions, remarks and Stale are not in the input to leak.
- **Input is delimited data.** The input has three parts, each delimited: the Shipper's question (and the last four turns of the conversation, see below), the fetched tracking data, and the current date and time in the Persona's time zone. Instructions say that the question and every string in the tracking data (a Shipper reference, a place name) is data, never an instruction. Output is plain text or sanitised Markdown, never HTML, with links only to the portal's own routes (the order's page).
- **No promises beyond the data.** The assistant states a fact only if the tracking data holds it, and says where it comes from (the Tracking status, the progress events, the ETA, the delivery window, the last update time, the Proof of delivery). It never states a date or time that the API did not return, a price, a cause or a reason for a delay, what Norvia will do, or a guarantee. The ETA is given as the estimate the data says it is ("the last update expects delivery at …"), never as a commitment, and with the last update time beside it. When the data has nothing that answers the question, it says "I have no information about that" and, for anything that needs a person, points the Shipper to Norvia's customer service. It does not guess and does not answer from general knowledge about transport.
- **A check after the model, not only an instruction.** The Agent returns a structured result: the answer text, and for each claim the field of the input it came from (a path into the tracking data). The portal then checks, in code, that every cited field exists and that every date, time, number and Transport Order number in the answer text also appears in the input. If a check fails, the portal drops the answer and shows the fixed "I have no information about that" text, counts the run as `Failed` with the code `AgentAnswerRejected`, and shows the Shipper nothing the model wrote. The check is unit tested with answers that contain an invented ETA, an invented price and a number from another order.
- **Dutch and English.** The assistant answers in the language of the question, Dutch or English, and in English when it cannot tell. In any other language it says, in English and Dutch, that it supports only those two. The five Tracking statuses have a fixed Dutch label in the instructions (Ontvangen, Ingepland, Opgehaald, Onderweg, Afgeleverd), so the Shipper sees the same word as on the screen. Times are written in the Persona's time zone in the form of that language. Both languages are in every evaluation set.
- **Conversation without storage.** A follow-up question works because the portal keeps the last four turns in the Persona's own browser session (the Blazor circuit) and sends them with the data fetched again for that question. Foundry holds no conversation, as ADR 0040 requires: the clients set `store: false` and create none. A question is a single response. A reload of the page starts a new conversation, and nothing about it is stored.
- **A separate Agent and identity with no role.** The assistant is its own published Agent, so it has its own Entra agent identity, which holds **no role at all** (a script gives it none, and a test asserts the list is empty). This is stricter than ADR 0040's rule for Shipper-facing text, which asks for a single tool: here the tool list is empty. The Agent's definition is a versioned file in the repo in the same format, with an empty tool list that the drift test keeps empty, and `Norvia.Agents` runs it. The Partner portal owns the `IAgentClient` port, as every host does. Locally the scripted fake plays it, and a setting can point it at a developer's own model, as ADR 0041 says; there is no MCP stand-in to start, because there is no tool.
- **Limits per Persona, in the portal.** The Foundry call does not pass API Management, so the per-Agent rate limit of ADR 0040 has nothing to count here. The portal enforces these, as estate parameters, and a Persona that exceeds one gets "You have asked a lot of questions. Try again in a few minutes." without a model call (`AgentRateLimited`, a span marked `Refused`):
  - **Rate:** 6 questions a minute and 60 an hour per Persona.
  - **Size:** a question is at most 500 characters, the fetched data at most 20 orders and 20 progress events per order (anything beyond is not sent, and the answer must not claim to have seen it), and the answer at most 400 output tokens.
  - **Cost:** a daily token budget per Persona (50,000 tokens) and one for the estate (500,000 tokens), counted from the usage Foundry returns on each response and reset at midnight UTC. When the estate budget is used up every Persona sees "Assistant unavailable" until it resets, and the Estate health check shows it.
  - **Fetch:** the tracking calls the portal makes for a question count against the Persona's tracking subscription (120 a minute, [failure behaviour](../architecture/failure-behaviour.md)), at most three per question.

  The counters are in the portal's memory, so the portal runs one replica while `Agents:Enabled` is on (a Container Apps setting, kept by a test on the Bicep). A restart resets them, which the daily estate budget and the model's own quota limit cover.
- **Tracking.** The portal records the run as a span with the Persona's ID, the run ID, the number of calls made, the tokens used and the outcome (`Answered`, `Refused`, `Failed`). Neither the question nor the answer is a tracking key or a log property: both are free text, and Foundry content recording stays off. The fetch calls carry the correlation ID as every call does ([coding guidelines §7](../coding-guidelines.md#tracking-contract)), so the answer is linked to the Message trail of what the model was given. The failure codes are `AgentUnavailable` (ADR 0040), `AgentRateLimited` and `AgentAnswerRejected`.
- **As-found toggles for the assistant.** The estate can be made as-found in these ways, and a health check should find them: no per-Persona rate or token limit, no estate token budget, no output check (the answer is shown as the model wrote it), the assistant's identity holding a role, a tool in its definition, or the portal passing a token or a Shipper ID to Foundry. `noAnswerCheck` and the limits are built in #878 and the rest in the Estate health check.
- **Evaluation.** The set has known answers drawn from the Simulator's Shippers and the as-found toggles, in Dutch and in English, and these cases: a Persona asks for another Shipper's order (the answer is "no information", and a test shows the other order is not in the input), asks for an ETA that the data does not hold, asks why a delivery is late, asks for a price, a Carrier or an Exception, and an injection in the question, in a Shipper reference and in a place name. A case fails if the answer holds a value that is not in the input, which the output check also catches. Like the others, the set never gates a merge ([evaluation](../operations/agent-evaluation.md)).

## Considered Options

- **An agent identity that calls a tracking tool with a Shipper ID parameter:** the model would choose the Shipper ID, so a prompt injection or a plain mistake could read another Shipper's orders. ADR 0005 says a partner-supplied identifier is never trusted, and the Agent's identity would need a role that reads every Shipper. Rejected.
- **Token pass-through: the Persona's token sent to an MCP tool through API Management:** the right Shipper is enforced by the token, as on the screen, and the model could ask follow-up questions of its own. But the Shipper's token would have to pass through Foundry (the Agent Service does not forward a caller's token to an MCP tool as a documented, supported feature, so it would need a spike first), a credential would sit in the model's tool path, and every tool call is another place a Persona's token can leak. The portal calling the API first gives the same authority with none of that. It costs the model the ability to look further, which this assistant does not need: the tracking screen has five statuses and a short list. Reconsider only with a spike and a new ADR if a real need appears.
- **An agent view and its own MCP server for the Shipper assistant, with a Shipper ID in the agent's token:** the Agent's identity is one identity for all Shippers, so the Shipper would still be a parameter the model fills in.
- **Give the model the TMS data behind the tracking API (a wider view) and let it filter:** it would answer more, but it would hold what ADR 0011 hides from the Shipper (the Carrier, Exceptions, remarks, Stale), and an instruction not to say it is not a boundary.
- **Trust the instructions for "no promises":** simpler, with no check code. But a model states a plausible ETA sometimes, and for an external user that is a promise. A check in code, with a fixed fallback, makes it a property of the design, as no write tools does for ADR 0040.
- **Rate limits in API Management only:** there is no Foundry call there to count, and the tool-call limit of ADR 0040 does not apply to an Agent with no tools. A limit on the tracking subscription alone would not bound the model's cost.
- **Store the conversation in Foundry for follow-ups:** less code in the portal, but it conflicts with `store: false` and ADR 0040's rule of no retained Shipper text, and it needs the sweeper for an external user's free text.

## Consequences

- The assistant can answer only about what the tracking screen shows, so it adds a way to ask, not new information. A Shipper who wants to know why something is late gets "I have no information" and Norvia's customer service, as before. What a Shipper hears about a problem still comes only from a Shipper notification the Planner chooses to send (P7, ADR 0011).
- A Shipper question about an order outside the first 20 and not named by a reference or number is answered "no information". The screen's own filters are the way to it.
- The output check can reject a correct answer (a date written in words, a number rounded). The rejection is visible as `AgentAnswerRejected`, and the fix is in the instructions or the check, never a looser check. The evaluation shows how often it happens.
- The portal's rate, size and cost limits are more portal code than ADR 0040's APIM policy, and the portal runs one replica while the assistant is on. Going to several replicas needs a shared counter and a new decision.
- The portal needs a Foundry client, so a Foundry SDK reference moves into the Partner portal's Infrastructure project. The architecture test of ADR 0040 allows exactly that, and the portal's other layers stay clean.
- A new page region and a new Foundry Agent are in the Partner portal, so its UI tests, opened with each slice, cover the assistant's panel in Dutch and English, the refusal, and the unavailable state.
- The documents that list the Agents, the identity and access matrix, the Partner portal's page, the local-vs-Azure table and the failure behaviour, are updated by the slices that build it (#878 and #879), not by this ADR.
