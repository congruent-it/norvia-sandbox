# The Simulator is its own application and sends only through the estate's real doors

The estate holds only a few hand-seeded days. The Simulator feeds it with representative orders, shipments and trips at a chosen volume, so demos, the Integration console, the Planner's lists and the Shipper views have something real to show. A Simulation run sends a Simulation plan, made from the run's settings and a seed, to the estate.

- **Its own application.** The Simulator is `src/Simulator` (Domain, Application, Infrastructure, Migrations and a Blazor Web project) with its own database for its runs, their plans and every step's outcome (ADR 0002). It is not the Integration console, which stores nothing and writes only dead-letter resubmits ([ADR 0017](0017-the-integration-console-reads-the-estates-telemetry-and-stores-nothing.md)). It is styled in Darkly's look like the console (the amendment to [ADR 0025](0025-the-integration-console-is-styled-with-tailwind-in-darklys-look.md)).
- **Only the estate's real doors** ([ADR 0001](0001-realistic-applications-integrated-only-through-ais.md), [ADR 0003](0003-http-in-events-out.md)). Shipper bookings go to the Norvia Partner API as the Shipper's Persona, with the token and subscription key the Partner portal gets for it ([ADR 0005](0005-partner-identity-comes-from-the-token.md)). The Planner's assignments, releases and handling of Exceptions go to the TMS API, as the Simulator's own identity holding the TMS API's manage role (locally it signs the token itself, as the TMS UI does). The Carriers answer their Carrier bookings, track their Shipments and prove their deliveries through the Partner API, each as its own Carrier Persona, with the token and subscription key the Partner portal gets for it, so a Carrier's step has the Message trail a real one has. The Drivers work their Trips through the Driver app API, each as the Driver, with a token whose one app role is the Driver ID, as the Driver app takes it from Entra ([ADR 0037](0037-drivers-sign-in-to-the-driver-app-with-entra-and-the-driver-id-is-their-app-role.md)); the API does what the Driver app's screens do, through the same commands. It never writes to a database or publishes to Service Bus itself, which an architecture test enforces. So every record it makes has a real Message trail.
- **The same code locally and in Azure.** Only the endpoints and credentials differ. Locally it signs the Persona tokens itself, as the Partner portal does ([ADR 0023](0023-locally-a-stand-in-plays-the-norvia-partner-api.md)). The Azure identity and sign-in are in [ADR 0042](0042-the-simulator-signs-in-with-easy-auth-reaches-the-estate-as-its-own-identity-and-plays-the-personas-and-drivers-through-entra-client-apps.md).
- **Master data stays in the seed file** (ADR 0002), extended where the Simulator needs it: Tuincentrum Groenrijk gets a Rate Card, so the Simulator can book for it. The Simulator generates only transactional data: Consignees, addresses, goods and dates. It chooses Lanes from the Shipper's Rate Card.
- **Reproducible.** The plan is made first, deterministically, from a visible seed; the preview is the plan that is sent. A run is not backdated: real paths stamp real time.
- **Guards.** One run is active at a time; a hard cap on the orders of a run and a cap on requests in flight, both settings with lower local defaults; and `Simulator:Enabled`, which is off unless the estate turns it on. A run is identifiable by its Shipper references, `SIM-<run>-<n>`. The reset is [below](#reset-estate).
- **Business outcomes only.** The failure mix is bookings Norvia refuses for business reasons: no Lane, a repeated or conflicting Shipper reference, invalid content. Infrastructure faults stay with the presenter's existing switches.

## Considered Options

- **Inside the Integration console:** one tool fewer, but the console would then store runs and write to the estate, which ADR 0017 rules out.
- **A seed script writing to the databases:** quick, but nothing it made would have a Message trail, and it would break the one-system-of-record rule (ADR 0002).
- **A load-testing tool:** it makes volume, not representative data with a log an audience can follow.

## Consequences

- A change to the Partner API's booking contract is made in the Simulator's format too, as it is in the Partner portal's (`PartnerBookingFormat`). A unit test checks every good booking against the booking schema.
- The Simulator needs a database, so the AppHost starts a migrations project for it before the Simulator, as for the other applications.
- **The Planner is rule-aware but not omniscient.** It reads the Own fleet's capacity from the TMS API once, keeps its own tally of what it puts on each day, and assigns to Own fleet where an order fits and to an active Carrier otherwise. The TMS only warns about Own fleet load, so the Planner's care is the Simulator's own rule, and what the TMS does refuse (a Carrier that has gone inactive, an order that was planned meanwhile) is logged as an outcome, not hidden. The Planner works through the accepted orders one at a time in plan order, which keeps its choices the same for the same seed and TMS state.
- **The Carriers are driven from the Simulator, so the Partner portal keeps quiet.** The Carrier Personas are seeded on the Manual answer and tracking modes: an automatic answer a few seconds after the Simulator's would answer the bookings it leaves unanswered on purpose, and an Auto-progress Persona would track a Shipment twice. The Partner portal's inbox keeps showing a request the Simulator answered as open, because the Simulator answers through the Partner API and not through the portal. A presenter who wants a Persona to answer by itself sets its mode on its Carrier page, as before, and sets it back.
- **The Carriers' steps are exact shares of the step before** (release, confirm, decline, track, Exception, deliver, Proof of delivery, cancel), picked by the seed once the Planner has assigned and the number of Shipments that went to a Carrier is known. Norvia processes tracking and Proofs of delivery after accepting them, so the Planner finds the Exceptions they open by asking the TMS for the Open Exceptions a few times, and cancels the Confirmed Carrier booking of a failed collection from its Exception, as ADR 0010 allows.
- **The Planner builds Trips the way a careful one would, and the TMS still decides.** The Simulator knows the Own fleet from the seed file (Vehicles with their capacity, Drivers with their licences) and the Shifts from the TMS's open days. It gives each Trip the smallest Vehicle that carries its Shipments and the Driver whose licence is worth the least, starts it at the start of the Driver's Shift and gives it a driving duration well inside the daily budget. What it can't know (an Absence, a Vehicle off the road, the weekly budget) the TMS refuses, and the refusal is logged as an outcome.
- **The Drivers' reports are taken at once and recorded later,** so a Driver waits, polling the Driver app, for the Trip to arrive and for the TMS to record the start before the Stops can be worked, and for the TMS to record the End Trip. The Driver app lets a Trip be ended when the delivery Stop of a Shipment whose collection failed has no outcome, as the TMS does.
- Its slices: Shipper bookings, Planner assignment (this one added the TMS API door), Carriers (this one added the Carrier Personas' calls, release, and the Exception calls), Trips and Drivers (this one added the Driver app API door and the Trip calls), then Azure (ADR 0042).

## Reset estate

A presenter starts each demo from an empty estate, and rebuilding the databases by hand is the only way to get one. Clear history removes only the Simulator's own runs and logs, so the Transport Orders, Shipments, Trips and Messages a run created stay in the TMS, the Partner portal and the Driver app. This replaces the earlier decision that there is no wipe (a fresh local run or a new azd environment was the reset).

- **A reset on the Simulator.** A **Reset estate** button on the Configure screen (Run role), behind a confirmation that says what goes and what stays. It returns the estate to a clean sheet: no Transport Orders, Shipments, Trips, Exceptions, Proofs of delivery or other transactional records in the TMS (whoever created them, so a hand-entered record goes too), no booking records in the Partner portal, no Trips or Driver reports in the Driver app, no runs or log lines in the Simulator, and the next run is number 1 with the Shipper references `SIM-1-1`. Reference data (Shippers, Carriers, Drivers, Vehicles, Rate Cards, Personas) is never deleted. It lives in the seed file, not in the databases.
- **Each application owns its door.** The apps never read each other's databases (ADR 0002) and the Simulator reaches the estate only through real doors, so the TMS API, the Partner portal and the Driver app API each expose a reset endpoint (`/v1/reset` on the two APIs, `/reset/v1` on the portal) and the Simulator orchestrates them. A `GET` says whether the application would take a reset now; a `POST` resets it and answers what it deleted, by kind. The TMS API and the Driver app API require the app role `Estate.Reset`, which the Simulator's identity holds; the Partner portal has no token validation of its own, so its endpoint takes an API key, as its other endpoints do.
- **Guarded by a setting, off by default.** `Reset:Enabled` is off unless the estate switches it on: on locally, and in Azure only where the estate sets it. An endpoint whose setting is off refuses with a 403 problem (`ResetDisabled`) and deletes nothing.
- **Service Bus: require quiet, don't drain.** The TMS API and the Driver app API peek the topic subscriptions whose consumers write records back (`Reset:QuietSubscriptions`, each `topic/subscription`) and refuse with a 409 problem (`SubscriptionBusy`), naming the subscription, while one holds an unprocessed message. Nothing is purged, so a late message can't re-create a record after the wipe. The Partner portal consumes nothing from Service Bus. The Simulator itself still never touches Service Bus: the apps look, and an architecture test keeps the Simulator's reset client to HTTP.
- **Order.** The Simulator checks quiet first (no active run, and every application willing and its subscriptions empty), then calls the applications, then clears its own runs, logs and run counter last. An application that refuses leaves the Simulator's history in place to explain what happened. The others are still told: a reset that stopped at the first refusal would leave them dirty, and every reset is safe to repeat.
- **What each application clears.** The TMS: Transport Orders and everything hanging off them, Shipments, Trips, Exceptions, Carrier bookings, Tracking events, Proof of delivery records and their files in blob storage, Shipper notifications and outbox Messages; it restarts its number sequences so numbers begin again at 1. The Planner's changes to Rosters, Absences and Off the road days go too, so the seed file's Rosters apply again; the Planning days are the calendar and stay. The Partner portal: what each Persona sent Norvia and received, and the Personas' answer and tracking modes, which return to the seed file's. The Driver app: the Trips it was sent, the Drivers' reports, its outbox and the demo settings. The Integration console stores nothing (ADR 0017): its Message trail for records that are gone ages out of telemetry and is not cleared.
- **Seed state is re-applied from the seed file, not re-booked.** After a reset the TMS does not book the demo's days (Over capacity day, Trip day, Trip execution) again: that is data a person or the Simulator creates, and a clean sheet means none. They are seeded only when the TMS first starts with `Seed:DemoData` on.
- **Reporting.** The screen says what each application deleted, by kind, or which application refused and why. A partial failure is reported as one and the reset can be run again.
- **In Azure** the estate owns the pieces. `identities.bicep` defines the app role `Estate.Reset` on the TMS API and on the Driver app API and grants both to the Simulator's identity. The Partner portal's key is the secret `reset-endpoint-key` in its vault, which the portal and the Simulator read; the reset path is outside the portal's Easy Auth gate, as the Persona endpoints are, because the key is its credential. The TMS API's identity gets Service Bus Data Receiver and the Driver app's identity Data Receiver on the `driver-reports` subscription, to peek. `Reset:Enabled` is off unless the environment sets `ESTATE_RESET_ENABLED_SETTING=true` before `azd provision`; `provision-estate.sh` hands it to the apps (not as an output, because the estate template is at ARM's limit of 64).
