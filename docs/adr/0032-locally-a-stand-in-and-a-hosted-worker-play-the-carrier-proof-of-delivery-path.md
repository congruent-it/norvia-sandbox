# Locally, a stand-in and a hosted worker play the Carrier Proof of delivery path

A Carrier's Proof of delivery is accepted at API Management by claim check, and reaches the TMS later through the Carrier Proof of delivery Logic App (ADR 0009). Locally there is neither API Management, nor a storage account, nor a Logic Apps runtime, so the same two local pieces split the path as they split the Carrier-tracking path (ADR 0031), with Azurite as the inbound container:

1. **`Norvia.Integration.LocalPartnerApi` plays the API Management operation** (ADR 0023). `POST /partner/v1/carrier-proofs-of-delivery` makes the same checks in the same order as `submit-carrier-proof-of-delivery.policy.xml` (subscription key, token, role `ProofsOfDelivery.Submit`, a body of at most 25 MB, a Carrier for `azp`), creates the correlation ID, stores the body unparsed as the blob named for the correlation ID in the `inbound-proofs-of-delivery` container, only then puts the blob's reference (`container`, `blobName`) on the `carrier-proof-of-delivery` queue, and answers `202 Accepted`. The message carries the application properties `correlationId`, `partyId` (the Carrier ID from the token), `sourceMessageId` (the Carrier's `documentId`, when it has one) and `flow` = `carrier-proof-of-delivery`. It calls neither the TMS nor a Logic App. When the blob or the reference can't be stored, it answers `503`, as the policy does, so the Carrier sends the Proof of delivery again.
2. **`Norvia.Integration.LocalProofOfDeliveryWorker` plays the Carrier Proof of delivery Logic App.** It reads the queue in peek-lock mode, fetches the blob the reference names, maps it with `CarrierProofOfDeliveryMap`, records it with the TMS in one multipart call as the identity holding `ProofsOfDelivery.Record` under the message's correlation ID, deletes the blob once the TMS accepted it, and settles the message by what the TMS answered, through `TmsProofOfDeliveryOutcome`, which the workflow's expressions are tested against: a recorded Proof of delivery completes the message; a client error dead-letters it with `DeadLetterReason` = the problem's failure code and `DeadLetterErrorDescription` = its message, not retried, and the blob is kept; a server error, throttling or timeout abandons it, so the queue delivers it again up to its maximum delivery count and then dead-letters it itself. A blob that can't be read dead-letters the message as `ProofOfDeliveryBlobMissing`, and content the map can't read as `UnmappableProofOfDelivery`; both fail the run and keep the blob.

The tracking contract's keys (coding guidelines §7) go into the worker's and the stand-in's logging scopes under the names the policy's trace metadata and the workflow's tracked properties use, so the Integration console finds a local trail in the Aspire dashboard's telemetry (ADR 0027).

## Considered Options

- **Extend `LocalTrackingWorker` to read the Proof of delivery queue:** it is named for, configured for and tested as the tracking flow, and holds the `TrackingEvents.Record` identity, not the Proof of delivery record role.
- **The stand-in putting the whole Proof of delivery on the queue:** the claim check is the point of ADR 0009, and the Service Bus emulator has the same message size limit as Service Bus.

## Consequences

- The stand-in is a second implementation of the policy and the worker a second implementation of the workflow. A change to the policy's checks, limit or application properties, or to the workflow's settling rules or tracked properties, must be made in both. `SubmitCarrierProofOfDeliveryPolicyTests` and `ProofOfDeliveryWorkflowTests` read the Azure side, and the stand-in's and the worker's unit tests check the same list.
- The workflow's `readBlob` and `deleteBlob` operations and its Service Bus operations can't be run without a Logic Apps runtime, and the policy's storage and Service Bus calls can't be run without API Management. The unit tests read the definitions; only a deployed run proves them.
- The local inbound container has no lifecycle rule: Azurite keeps a blob a failed message leaves behind until the emulator's data is cleared. In Azure the rule deletes it after `integrationRetentionDays`.
- Neither runs in Azure: `azd` never deploys them.
