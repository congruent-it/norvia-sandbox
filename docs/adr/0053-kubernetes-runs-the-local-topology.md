# Kubernetes runs the local topology

**Status: Proposed.** The sandbox runs under Aspire on a developer's machine, or in Azure. This adds a third place: any conformant Kubernetes cluster (tested on K3S). It is decided in #923 and the deployment tooling comes from the spike in #924 ([findings](../research/kubernetes-publisher-spike.md)).

What runs there is the **local topology** of [local-vs-azure.md](../architecture/local-vs-azure.md): the applications plus the stand-ins and emulators that already play Azure's pieces under Aspire, as pods. It is not a third copy of the Azure estate. The as-found toggles, the alerts and the real Estate health check stay Azure-only, and the health check reads its snapshot as it does under Aspire.

## Decision

- **No Azure at runtime.** No Azure account, Entra, Key Vault, Foundry or Application Insights. Everything an Azure piece does is played by what plays it under Aspire. Nodes are amd64, because SQL Server and the Service Bus emulator have no ARM images.
- **A shared cluster and one namespace.** Other applications run on the same cluster. Everything Norvia deploys is in the `norvia` namespace, which has a default-deny `NetworkPolicy`, an internal-only ingress, Secrets limited to its service accounts and a `ResourceQuota` (#938). Cluster-scoped pieces (the ingress controller, the cert-manager issuer, the storage class, CRDs) are chart values or are installed once, outside the chart.
- **The workers are pods, not Dapr Workflow.** The `Local*Worker` hosts run as Deployments, as they run as hosted services under Aspire. Rewriting the flows on Dapr Workflow would make a third implementation of each (the Logic App, the worker, and that), which ADR 0031 already warns against. A Dapr pilot on one flow is a separate issue. The control plane of Dapr, if it comes, is installed outside the chart.
- **The Service Bus emulators are kept, two of them, as under Aspire.** Each accepts 10 connections and every application holds one, so the AppHost's split of topics and queues between `messaging` and `messaging-2` stays (see local-vs-azure.md). 16 projects call `Azure.Messaging.ServiceBus` directly, the Driver reports consumer needs sessions (ADR 0016) and the console's dead-letter operations use the SDK. Dapr pub/sub is a separate, optional feature (#937).
- **SQL Server and Azurite on persistent volumes, with no backups.** SQL Server is one StatefulSet holding the five databases on a PVC of the cluster's storage class. Azurite holds the blobs on its own PVC. There is no backup and no high availability: a lost volume is rebuilt from the seed file, as a developer's machine is.
- **`LocalAuth:Allowed` is the opt-in for local sign-in.** There is no identity provider. A named setting, `LocalAuth:Allowed`, independent of the environment name, lets the local operator sign-in and the local token-signing key run outside Development. It is off by default, and the guards of ADR 0026 and ADR 0037 (refusing to start outside Development) stay on until it is set. It is **safe only when Norvia's ingress is not reachable from the public internet and no other namespace can reach Norvia's pods.** Anyone who can reach the ingress is signed in as an operator holding both console roles, and anyone who can reach a pod can get a token signed by the local key. The chart's default-deny policy and internal-only ingress (#938) are what make the condition true, so a cluster where they cannot be enforced (a CNI without `NetworkPolicy`) is not a place to set it.
- **The agents are the scripted fakes.** `Agents:Enabled` stays off by default, as under Aspire, and no model is called.
- **The edge is chart values.** The ingress controller class (Traefik on K3S is the tested default), the base domain, the TLS issuer from cert-manager and the image registry are all values of the chart, with no default that points at one cluster.
- **Telemetry goes to the standalone Aspire dashboard**, the same as locally, with the same limit: it holds only the current session. Retention across restarts (Tempo, Loki and a trail source for the console) is a separate issue.
- **One smoke script** (a booking, tracking, a Proof of delivery) runs through the ingress after every deploy.
- **The deployment is a hand-written Helm chart in the repo, applied with `helm upgrade --install`.** The AppHost stays as it is: Azure Container Apps in publish mode, Aspire locally. It does not get a second AppHost, and it does not get a third mode. The chart is plain, so Flux or Argo CD can take it later as a `HelmRelease` or an `Application` without a change, once the cluster owner has a GitOps controller. `kubectl apply` of rendered manifests is not used, since it cannot order the migrations before the applications or prune what was removed. The publisher's output is used once, as a checklist of each application's settings, to start the chart.
- **The chart and the AppHost are kept together by a check, not by a convention.** A test starts the AppHost's model in run mode (`Aspire.Hosting.Testing`), takes each project's environment variable names and compares them with `helm template`'s output for the same project, ignoring the names the chart replaces on purpose (connection strings, `LocalAuth:Allowed`). This is the cost of writing the settings twice.

## Considered Options

The spike ran Aspire 13.6.5's Kubernetes publisher (`Aspire.Hosting.Kubernetes`, preview only) against the AppHost and a compact AppHost of the local topology.

- **A second AppHost sharing the project references:** it publishes, and writes a chart of 114 files. But the real wiring is the 1,224-line `AppHost.cs` (personas, keys, each worker's settings, filters), which a second file copies, and its output has to be patched afterwards.
- **A third mode in the current AppHost:** one file. But `IsPublishMode` is binary and is hard-wired to Azure Container Apps, the real AppHost does not publish until every resource names a compute environment, and any Azure resource left in the model writes Bicep and an empty value. It would put Kubernetes, Azure and run mode into the file that `azd` and the integration tests depend on.
- **A hand-written Helm chart (chosen):** the AppHost does not change. The chart is a second place that knows the applications' settings, which the check above covers.

The publisher's chart is missing or wrong for exactly the pieces #923 and #938 ask for. It makes each migration a Deployment that restarts forever, not a Job. It drops `WaitFor`, the health checks and the start order. It turns `WithDataVolume()` into `emptyDir`, so the databases vanish with the pod. It drops the Service Bus emulator's `Config.json` without a word. It generates no namespace, `NetworkPolicy`, `ResourceQuota`, ingress or limits. It writes values the AppHost computes at publish time into `values.yaml` as literals, including a developer's seed path and the Carriers' keys, which then sit in a ConfigMap. Each of these has to be added after the fact in A and B, and is the work itself in C. A spike on one preview version is also no evidence that the next one keeps its output stable.

- **Dapr Workflow for the flows:** Kubernetes-native. But it is a rewrite of 13 flows, the third implementation of each (ADR 0031).
- **Dropping the Service Bus emulators for Dapr pub/sub:** fewer pieces to run. But 16 projects use the SDK directly, the Driver reports consumer needs sessions, and whether the Dapr component's session settings fit ADR 0016 is unverified.
- **An identity provider in the cluster:** no `LocalAuth:Allowed`. But it is a new thing to run and configure, and the sandbox's identity is the local key in every place that has no Entra.
- **A `LocalAuth:Allowed` that is on whenever the cluster is not Development:** nothing to set. But it would sign anyone in on any cluster, so it is an explicit opt-in with a condition recorded here.

## Consequences

- ADR 0004 (Bicep owns the estate, Aspire owns the apps) is about Azure and is not superseded. The Kubernetes deployment is outside it: the chart owns the apps there, and no estate exists. [local-vs-azure.md](../architecture/local-vs-azure.md) links this ADR.
- The chart and the AppHost both know each application's settings. The check keeps them together, and a new setting in the AppHost fails it until the chart has it.
- The chart owns what the publisher did not generate: the migrations as Jobs or hooks that finish before the applications, probes, the PVCs, a ConfigMap for the emulators' `Config.json` and the seed file (or an image that holds them), the namespace, policies, quota, limits and the ingress.
- The Driver reports "disabled" flag file (`DriverReports__DisabledFlagPath`) is a file the Partner portal creates and `LocalDriverReportsWorker` reads, so under Aspire they share a disk and in two pods they do not. It needs a design decision (a shared volume, or the flag moves to the TMS or a table) in the chart's slice, and is not made here.
- Setting `LocalAuth:Allowed` is a statement that the condition above holds. #938 enforces the condition with the network policy and the internal-only ingress.
- Telemetry does not survive a restart, and the Estate health check shows only its snapshot, as under Aspire.
- A lost SQL Server or Azurite volume loses the data, and the seed file is the way back.
- **Not verified:** `helm lint` and `helm template` on any chart, anything on K3S, `PublishAsKubernetesService`, and a stable Aspire Kubernetes package. The spike had no `helm` or `kubectl`.
