# Consignees track with a tracking code in a link and no token

**Status: Proposed.** Consignee tracking was left out of P8 on purpose because it needs another identity model ([P8 Deferred](../processes/tms/p8-shipper-visibility.md#deferred)). This is that model (#981). The tracking link and screen (#982) and the Consignee notification (#983) are built on it.

A Consignee is not a party with a system, a contract or a sign-in. It is whoever stands at the delivery address, and Norvia holds only its name, address and phone number. ADR 0005 takes a partner's identity from an Entra token that belongs to a Persona's client app, so it cannot apply: there is nobody to issue a token to, and one client app per Consignee would make no sense. Whoever holds the link is the Consignee, and the link has to be safe to hand out by email.

## Decision

- **A tracking code per Transport Order.** The TMS generates it when the Transport Order is Accepted and stores it on the Transport Order. It is 16 characters of Crockford base32 from a cryptographic random source (80 bits), and has no relation to the Transport Order number or any other field, so it cannot be guessed or derived. It is not the Shipper reference, which the Shipper chooses and may share.
- **The Consignee is not a Persona.** A Persona is a Shipper or a Carrier with an Entra client app and app roles. The Consignee gets none: no client app, no app role, no `azp`. Authority comes from the code alone, and the code opens one Transport Order, nothing else. The glossary's Persona and Persona switcher terms are unchanged, and Consignee tracking has no Persona switcher entry.
- **The link opens a Partner portal page that sits outside the Entra gate.** The link is `/track/{code}` on the Partner portal. ADR 0024's gate would refuse a Consignee, so this route, like each Carrier's booking endpoint, is left outside it. The page reads no Persona and no signed-in user. What it can show is limited by the projection below, because anyone with the code can read it.
- **A separate, token-less operation in API Management.** The portal calls API Management with its own subscription key from a `consignee-tracking` product that has one read operation, "Get a Consignee's view by tracking code". No JWT is validated, and no `Tracking.Read` role applies, since the Shipper operations stay as they are and a Consignee code never opens them. API Management passes the code and a correlation ID to the TMS with its managed identity, and an API Management policy changes the format only (ADR 0011).
- **What the Consignee sees.** The Shipper's projection (ADR 0011) with the Shipper-only items taken out: the Tracking status (the five statuses, never moving backwards), the progress Tracking events (type, event time, city and country), the ETA and the delivery window (the agreed one if there is one), the last update, and the collection and delivery places. The current Proof of delivery is shown as received by, delivery time and condition, **without its files**: the Consignee signed it and the files can hold other people's names and signatures. The Consignee never sees the Shipper reference, the Shipper's name, the Carrier, the Shipment number, Exceptions, remarks, Stale or a price. The TMS makes this projection, in its own read model for the Consignee, not by filtering the Shipper's.
- **Lifetime.** The code works from Accepted. It expires 30 days after the Transport Order's Delivered, or after its last progress Tracking event if it is never delivered. It has no revocation: a link that has gone to the wrong person is the Shipper's problem to take up with the Planner, who can have the TMS issue a new code, and the old one stops at once. This keeps the model to one stored field and one rule.
- **A wrong, expired or replaced code is one answer.** The API returns `TrackingCodeNotFound` with the same status, body and timing in all three cases, so it does not say whether a code ever existed. The page says "We can't find this shipment. Check the link, or contact the sender."
- **Abuse limits, at the edge.** API Management applies `rate-limit-by-key` on the caller's client IP (60 calls a minute) and a second, lower limit on `TrackingCodeNotFound` answers per client IP (10 a minute), so guessing is slow, and a guess fails because the code space is 2^80. Both are policy and need no TMS support. A rate-limited call is logged `Refused` with the code `RateLimited`.
- **Nothing personal in the logs.** The tracking code is a credential. It is never logged: the TMS and API Management log the Transport Order number it resolved to, or `none` for a miss, and the code appears in no trace, URL log or event. The page sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, so a code in the URL does not leak to an outside site or stay in a cache.

## Considered Options

- **A Persona for each Consignee, or one shared Consignee Persona with an Entra token:** it keeps ADR 0005 whole. But there is nobody to issue a client app to, a shared one would give every Consignee every other Consignee's view, and a token would put a sign-in in front of someone who only wants to know where a parcel is.
- **The Transport Order number or the Shipper reference as the link:** nothing to store. But both are guessable or in the Shipper's hands, and anyone who had one could read the Transport Order.
- **A signed link, such as an HMAC over the Transport Order number with an expiry:** nothing stored, and expiry comes for free. But replacing a leaked link needs a key rotation that breaks every link, and the TMS would hold a signing key to look after. A stored random code can be replaced one at a time.
- **A one-time code sent to the Consignee's phone or email before the page opens:** stronger, and needs the notification channel from #983. But it puts a second step in front of a status page, and it makes tracking depend on notifications. It can be added later behind the same route.
- **The Consignee gets the Shipper's view and files:** one projection to maintain. But it shows the Shipper reference, and Proof of delivery files that a code-only reader should not see.

## Consequences

- The Partner portal now has anonymous routes. ADR 0024's text, [identity-and-access.md](../architecture/identity-and-access.md) and the C4 page must say so, and the gate's exception list is `/health`, `/alive`, each Carrier's booking endpoint and `/track/{code}`.
- A leaked link shows a Consignee's view of one Transport Order to whoever has it, until it expires or is replaced. It has no names or phone numbers (the projection has no Consignee personal data), no Carrier and no price, so what leaks is a Tracking status and two cities.
- The Transport Order gains a tracking code and a replace-code action for the Planner, and a Canonical Model field. The ADR leaves the Planner's screen for #982.
- The Consignee notification (#983) sends the link and nothing else, so a lost email leaks no more than the link.
- #982 and #984 say "revoked": it means replaced here, since there is no separate revocation. Both change to say so.
- The Consignee page is a plain HTML page with a small inline style, not Fluent UI: everything the portal serves except `/track/*` is behind the Entra gate, so a script or stylesheet would not load for a Consignee. It has no scripts, and so no interactive components.
- The two abuse limits are per end-user client IP, which the Partner portal passes on in `X-Client-IP`, since API Management sees only the portal as its caller.
- Shipper tracking is untouched: the operations, roles and projection of P8 do not change.
