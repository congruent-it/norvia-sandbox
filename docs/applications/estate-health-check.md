# Estate health check

Part of the [applications](README.md). What it does and how to run it is in [operations/estate-health-check.md](../operations/estate-health-check.md).

## APIs

The Estate health check has **no API for its callers** and publishes no OpenAPI document. It is a Blazor UI the Integration operator signs in to (the roles `HealthCheck.Run`, `HealthCheck.Read` and `HealthCheck.Cost`; a local operator under Aspire, Easy Auth in Azure; see [identity-and-access.md](../architecture/identity-and-access.md)). Its only HTTP endpoints besides the UI's own assets are the `/health` check that Aspire calls and, while the Agents are on, the agent API below. Nothing else in the estate calls the app, so there are no other consumers to list.

- **The agent API, `/agent/v1`.** Mapped only while `Agents:Enabled` is on (off by default). A read-only view of the health check for the Estate health-check agent, behind a bearer token for the role `HealthCheck.Agent.Read` that no operator holds: `GET /agent/v1/checks` runs the checks and answers the Findings, each with its ID, the Check's ID, title, rule and severity, the evidence (subject and detail, masked), the as-found toggle and the fix. It answers an empty list when every Check passed. It has no write route, and it takes no input. Locally the MCP stand-in, `Norvia.Integration.LocalAgentMcp`, is its one caller, as the Agent's identity; in Azure it is API Management, which calls it as its own identity with an Entra token for the app's agent API (role `HealthCheck.Agent.Read`) and names the Agent in the `X-Agent-ID` header. It publishes no OpenAPI document of its own: its tool is listed in [health-check.tools.json](../../contracts/agent-mcp/health-check.tools.json) ([ADR 0040](../adr/0040-agents-read-the-estate-through-api-management-have-no-write-tools-and-their-own-identity.md)).
- **What it calls.** Locally it reads a snapshot of the estate's configuration embedded in the app, and calls no other application. In Azure it reads Azure Resource Graph (the Azure Monitor alert rules) and Service Bus's management plane as its own managed identity, which holds Reader on the estate's resource group, and asks the Estate health-check agent in Foundry as that identity too. For the cost view (`ICostReader`, [#504](https://github.com/congruent-it/norvia-sandbox/issues/504)) it reads Cost Management's daily actual cost per resource as that identity (Cost Management Reader on the resource group) and calls the TMS API's `GET /v1/transport-orders/volume` with the role `TransportOrders.Volume.Read`, the one TMS role it holds. Locally the cost is a modelled snapshot ([as-found.md](../operations/as-found.md#the-cost-shape), chosen by `Estate:CostSnapshot`, `fixed` by default) and calls nothing.
- **The cost reader's answer.** Whole past days only, in EUR, per resource per day, with the Transport Orders of that day beside it. Cost Management settles a day about a day late, so **yesterday is marked `provisional`** and **today is left out** (it is not a whole day, and its Transport Order count would not match); the page shows the lag and never a guess. A bill that is not in EUR is refused, not converted. Locally the snapshot has no lag and no day is provisional. Resource names come from the estate and travel as fields, never inside prose a model reads.

## Database

The Estate health check stores nothing: a result lives in the page session, so it has no database.
