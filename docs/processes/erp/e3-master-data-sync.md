# E3 Master-data sync

Finance changes a record the ERP owns, and the change is replicated to the TMS through Azure Integration Services. The ERP owns the six master-data entities (ADR 0002, 0006, 0013, 0014) and the TMS holds replicated read copies; neither calls the other (ADR 0001, ADR 0003). Terms are in [GLOSSARY.md](../../../GLOSSARY.md); the design is [ADR 0050](../../adr/0050-the-erp-replicates-each-master-data-change-to-the-tms-as-one-whole-record-event-with-a-revision.md), and locally [ADR 0051](../../adr/0051-locally-a-hosted-worker-plays-the-e3-master-data-sync-logic-app.md) plays the Logic App.

| | |
|---|---|
| **Trigger** | Finance creates or edits a record in the ERP |
| **Outcome** | The TMS's copy is the ERP's record, at the same Master-data revision |
| **Integrations touched** | Service Bus (`master-data-events`), the master-data sync Logic App, the TMS API |
| **Role** | Finance edits. The Logic App's identity holds `MasterData.Replace` on the TMS API and nothing else |

## Process model

1. **Edit.** Finance creates or edits a record in the ERP UI's master-data forms (Shippers, Carriers, Rate Cards, Carrier Rate Cards, Vehicles and Drivers each have a **New** link and an **Edit** link per row). A form checks what it can before it sends: the required fields, a new record's ID and a Vehicle's registration being unique. A card's versions are edited as JSON in the shape of the API's body. The UI reads in process and sends the save through the ERP API as its own identity, which holds `MasterData.Manage` (ADR 0028's split). The ERP API's `PUT /v1/shippers/{id}`, `PUT /v1/carriers/{id}`, `PUT /v1/rate-cards/{id}` or `PUT /v1/carrier-rate-cards/{id}`, `PUT /v1/vehicles/{id}` or `PUT /v1/drivers/{id}` (role `MasterData.Manage`) creates or edits the record. A Rate Card or Carrier Rate Card is saved with its whole list of dated versions, which must not overlap in time, and a Shipper, Carrier, Vehicle or Driver has one. A Vehicle has a registration, a type (Van, RigidTruck or TractorWithTrailer), a payload and pallet places; a Driver a name and licence categories (B, C, CE). A new record starts at Master-data revision 1; an edit raises it by one. A repeat of what the record already is, a card's versions or a Driver's licences compared whatever their order, changes and publishes nothing.
2. **Publish.** In the same transaction the ERP writes the whole record to its outbox as the `Shipper` event ([shipper.v1](../../../contracts/canonical-model/shipper.v1.schema.json)), the `Carrier` event ([carrier.v1](../../../contracts/canonical-model/carrier.v1.schema.json)), the `RateCard` event ([rate-card.v1](../../../contracts/canonical-model/rate-card.v1.schema.json)) the `CarrierRateCard` event ([carrier-rate-card.v1](../../../contracts/canonical-model/carrier-rate-card.v1.schema.json)), the `Vehicle` event ([vehicle.v1](../../../contracts/canonical-model/vehicle.v1.schema.json)) or the `Driver` event ([driver.v1](../../../contracts/canonical-model/driver.v1.schema.json)) on `master-data-events`, under a correlation ID created for the change, with `flow` `master-data` and the record's ID as `partyId`.
3. **Replicate.** The Logic App's `master-data-sync` subscription admits `Shipper`, `Carrier`, `RateCard`, `CarrierRateCard`, `Vehicle` and `Driver` events. It maps the event to `PUT /v1/shippers/{id}`, `/v1/carriers/{id}`, `/v1/rate-cards/{id}`, `/v1/carrier-rate-cards/{id}`, `/v1/vehicles/{id}` or `/v1/drivers/{id}` on the TMS API with the record but for its ID (a Shipper's or Carrier's name, active flag and revision; a card's party, revision and full list of versions; a Vehicle's registration, type, capacity, active flag and revision; a Driver's name, licences, active flag and revision), with the event's correlation ID, as its own identity, retrying a server error, a timeout, `408` and `429` three times (5 s up to 20 s).
4. **Apply.** The TMS upserts the record, so a new one appears; a Rate Card or Carrier Rate Card replaces the TMS's whole list of versions. It keeps the latest revision it applied and answers `200` with `applied: false`, changing nothing, to a revision that is not higher. A replaced card changes only what is rated after it arrives: a Transport Order already Rated keeps its Freight Charge, and re-rating is [#908](https://github.com/congruent-it/norvia-sandbox/issues/908).

A Shipper, Carrier, Vehicle or Driver is never deleted, only made inactive. Making one inactive stores `Active = false` and nothing else. For a Vehicle or Driver the TMS keeps availability apart from the replica ([ADR 0014](../../adr/0014-the-erp-owns-vehicles-and-drivers-the-tms-owns-their-availability.md)): a replaced Vehicle or Driver edits no Roster and opens or closes no day, it drops out of the days opened after that, and a Trip already using it is flagged Needs a Vehicle or Needs a Driver by the availability check P11 applies to every change to a Trip and again at Dispatch.

## Failure behaviour

| What fails | Result |
|---|---|
| The TMS doesn't answer, or answers a server error, `408` or `429`, after the retries | Dead-lettered as `TmsUnavailable` |
| The TMS refuses (any other client error, a conflict included) | Dead-lettered as `TmsCallRefused`, with the TMS's message |
| The message isn't a `Shipper`, `Carrier`, `RateCard`, `CarrierRateCard`, `Vehicle` or `Driver` event the TMS can replace a record from | Dead-lettered as `MasterDataUnreadable`, nothing sent |
| An older or repeated revision arrives | `2xx`, nothing changed |
| A card's versions overlap in time, or can't be read | Dead-lettered as `TmsCallRefused` (`RateCardVersionsOverlap` or `MasterDataUnreadable` in the TMS's message); the ERP refuses such a card before it publishes |

A dead-lettered message is resubmitted from the Integration console to the `master-data-sync` subscription only.
