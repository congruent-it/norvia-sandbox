# Norvia sandbox

A working integration estate for a fictional company, **Norvia Logistics B.V.**, a road freight and warehousing company based in Rotterdam. The sandbox builds Norvia's applications (TMS, WMS, ERP, Driver app, Partner portal, Integration console) as realistic .NET applications. They talk to each other only through Azure Integration Services: API Management, Logic Apps and Service Bus. The point is to demo the integration layer. Someone clicks through a UI in one application, watches the result appear in another, and sees exactly where it failed when it doesn't.

The estate can also run *as found*, reproducing the problems a health check would find (a missing dead-letter alert, a mapping that can't handle a Carrier status, marketplace orders routed to the wrong system), and fixing them one at a time.

> **Status:** first build. The TMS takes in a Transport Order through its intake API and publishes `TransportOrderAccepted`, running locally under Aspire. The TMS UI lists the Transport Orders waiting for planning for the Planner and the rejected bookings for Customer service, both live, and shows each one in full; a Role switcher moves between the two without a login. The partner booking format and the intake map to the Canonical Model exist and are tested with sample messages.
>
> `azd up` deploys the estate (Service Bus, monitoring, Entra, the intake Logic App, API Management) and the TMS to Azure. A Shipper books through the Norvia Partner API in API Management with a subscription key and an Entra token; API Management takes the Shipper from the token and passes the booking to the intake Logic App, which maps it, submits it to the TMS as the one identity holding the intake role, and answers in the partner format.
>
> In the Partner portal a presenter plays a Persona: as Brouwer Dranken they book a transport and see the Transport Order number, or every reason Norvia rejected it, while the order appears in the TMS UI beside it. As Van Dijk Transport, a Carrier, the booking is refused. In Azure the presenter opens both UIs from their own browser behind an Entra sign-in that admits only them ([ADR 0024](docs/adr/0024-the-demo-uis-are-public-behind-an-entra-gate-for-the-presenter.md)). Locally a stand-in plays API Management and the intake Logic App ([ADR 0023](docs/adr/0023-locally-a-stand-in-plays-the-norvia-partner-api.md)), so the whole path runs under Aspire.
>
> The Integration console signs in the Integration operator and searches Message trails by correlation ID or business key in the estate's telemetry and opens one trail's hops in time order, fan-out indented, reading it as its own managed identity; in Azure Entra admits only users holding one of its app roles, and it refuses anyone without `IntegrationConsole.Read`.

## Systems

| System | Owns |
|---|---|
| **TMS** | Transport Orders, Shipments, Trips, Carrier bookings, Own fleet availability |
| **WMS** | Fulfilment Orders, Inventory |
| **ERP** | Shipper, Carrier, Vehicle and Driver master data, Contracts, Rate Cards, invoicing. So far it loads and shows the Shippers, Carriers, Rate Cards and Carrier Rate Cards, read-only, and records Billable lines through its billing API, which the Billing Logic App calls with each `TransportOrderBillable` and the Carrier cost Logic App with each `CarrierCostIncurred`, and lists the Waiting ones, issues Shipper invoices, and shows whether each was sent to the Shipper |
| **Driver app** | Nothing. Drivers receive Trips and report Stops through it |
| **Partner portal** | Nothing at Norvia. It plays every outside Shipper and Carrier as a Persona |
| **Integration console** | Nothing. It reads the estate's telemetry |
| **Simulator** | Its own runs and logs. It feeds the estate with representative orders, plans them as the Planner and has the Carriers answer, track and deliver them, through its real doors |

Every concept has one system of record ([ADR 0002](docs/adr/0002-one-system-of-record-per-concept.md)). Until the ERP's master-data sync exists, a shared seed file supplies master data to both the ERP and the TMS.

## Architecture in brief

- **Integrated only through AIS.** Applications never call each other directly ([ADR 0001](docs/adr/0001-realistic-applications-integrated-only-through-ais.md)). All messages use Norvia's Canonical Model.
- **HTTP in, events out.** An application receives commands as HTTP calls from a Logic App and publishes what happened to Service Bus. It never consumes from Service Bus. Queries go from API Management straight to the application's API, with no Logic App on the path ([ADR 0003](docs/adr/0003-http-in-events-out.md)).
- **Identity from the token.** A partner's identity comes from its Entra token, never from the payload ([ADR 0005](docs/adr/0005-partner-identity-comes-from-the-token.md)).
- **Bicep owns the estate, Aspire owns the apps.** Hand-written Bicep in `infra/` provisions the AIS estate and every broken/fixed toggle. .NET Aspire runs the applications. azd deploys both ([ADR 0004](docs/adr/0004-bicep-owns-the-estate-aspire-owns-the-apps.md)).
- **Every flow is traceable.** Each flow records the same tracking keys (correlation ID, flow name, business keys, outcome), so the Integration console can follow any message end to end ([ADR 0017](docs/adr/0017-the-integration-console-reads-the-estates-telemetry-and-stores-nothing.md)).

## Tech stack

.NET 10 with Clean Architecture, EF Core with Ardalis repositories and specifications, Minimal APIs, and Blazor with Fluent UI components for web UIs, styled with Tailwind CSS in the TMS UI, the Partner portal, the Integration console and the Simulator. Tests use xUnit, NSubstitute, bUnit, Testcontainers and Playwright, with an 80% line coverage gate on unit tests. The Azure side is API Management, Logic Apps, Service Bus, Key Vault, Entra ID, Application Insights and Container Apps. See [docs/coding-guidelines.md](docs/coding-guidelines.md) for the full rules.

## Running it locally

Needs the .NET 10 SDK, Docker, and Node.js 20 or later (the TMS UI's, the Partner portal's, the Integration console's and the Simulator's stylesheets are built with Tailwind CSS, [ADR 0018](docs/adr/0018-the-tms-ui-is-styled-with-tailwind-in-flatlys-look.md), [ADR 0022](docs/adr/0022-the-partner-portal-is-styled-with-tailwind-in-luxs-look.md), [ADR 0025](docs/adr/0025-the-integration-console-is-styled-with-tailwind-in-darklys-look.md)).

```bash
dotnet run --project src/Norvia.AppHost      # TMS API and UI, Partner portal, Integration console, the local Partner API, migrations, SQL Server and the Service Bus emulator, with the Aspire dashboard
for p in $(find tests -name '*.UnitTests.csproj' -o -name '*.ArchitectureTests.csproj' | sort); do dotnet test "$p"; done   # unit and architecture tests
for p in $(find tests -name '*.IntegrationTests*.csproj' -o -name '*.UiTests*.csproj' | sort); do dotnet test "$p"; done        # integration and UI tests, one project at a time
```

Run the integration and UI tests one project at a time, as CI does, and not with `dotnet test Norvia.slnx`: each of them starts AppHosts of its own (SQL Server and the Service Bus emulator in Docker, about 6 GB each), and the solution run starts those of several projects at once. On a 64 GB machine that ran out of memory, so containers failed to start, Chromium crashed and the desktop's out-of-memory daemon killed applications. Run one such project at a time, and one test session at a time.

There is no Entra locally. The TMS trusts JWTs signed with the AppHost's secret parameter `local-token-signing-key` (issuer and audience in [LocalTokens.cs](src/Norvia.AppHost/LocalTokens.cs)), so submitting a Transport Order needs a token signed with that key, with the `TransportOrders.Intake` role and the local intake Logic App's client ID as `azp`. The integration tests issue their own.

Set `NORVIA_TEST_LOG_FILE` to a path to keep the TMS's own logs from an integration test run.

The TMS UI (`tms-web` on the Aspire dashboard) reads the TMS database through the TMS query side; it takes in nothing and publishes nothing. It changes things, such as Customer service's re-rate and the Planner's assignment of Transport Orders to Own fleet or a Carrier, only through the TMS API, as its own identity: in Azure its managed identity holds the TMS API's `TransportOrders.Manage` role, and locally it signs its own token with `local-token-signing-key`. Its lists of Transport Orders waiting for planning, of rejected bookings and of rating exceptions read again every second (`LiveList:RefreshInterval`), so a new one appears without a refresh. The Role switcher in the navbar remembers the chosen role in a cookie, and `/` opens that role's view: the Planner's by default. The UI tests drive it with Playwright in headless Chromium, which their fixture installs on the first run. They keep a trace and a video of each failed test under `TestResults/playwright`, or under `$NORVIA_UI_TEST_ARTIFACTS/playwright` when that is set.

The Partner portal (`partner-portal-web` on the Aspire dashboard) plays every Shipper and Carrier as a Persona; the Persona switcher in its navbar chooses one, and `/` opens the booking form of the one last chosen. It calls the Norvia Partner API only. Locally that is `partner-api`, a stand-in for API Management and the intake Logic App that checks the same subscription key, token and role, and then maps the booking and calls the TMS with the Logic App's own code ([ADR 0023](docs/adr/0023-locally-a-stand-in-plays-the-norvia-partner-api.md)). The AppHost gives each Persona in the seed file a client ID and a subscription key for the run, and the portal signs each Persona's token with `local-token-signing-key`, as Entra would, with the submit role for Shipper Personas only. The portal keeps each Persona's bookings and Norvia's answers in its own database, as the outside party's records.

The Driver app (`driver-app-web` and `driver-app-api` on the Aspire dashboard) is the Driver's own system, with a database of its own. Its API takes a Trip version (`POST /v1/trips`, the Canonical Model's `TripDispatched` shape) and keeps the latest per Trip number; an equal or lower version is acknowledged and ignored. Its screens sign a Driver in with Entra ID in Azure (the Driver ID is the user's app role) and locally with a stand-in that lists the seeded Drivers ([ADR 0037](docs/adr/0037-drivers-sign-in-to-the-driver-app-with-entra-and-the-driver-id-is-their-app-role.md)), then list that Driver's Trips by day, with their Stops, always the latest version. On the day of a Dispatched Trip the Driver can press **Start Trip**: the Driver app publishes `TripStartReported` through its outbox, the Driver reports Logic App (locally `driver-reports-worker`, [ADR 0038](docs/adr/0038-locally-a-hosted-worker-plays-the-p12-driver-reports-logic-app.md)) has the TMS start the Trip and tells the Driver app, and the Trip card shows the report as Sending, Recorded, Refused or Not recorded ([P12](docs/processes/tms/p12-trip-execution.md)). Its *Driver app unavailable* Fault, switched on from the Partner portal's presenter panel for a few minutes (the `Demo.Fault` role guards `/v1/faults`), makes the Trip endpoint return 503. It never calls the TMS: Trips reach it through the Trip dispatch Logic App ([P11](docs/processes/tms/p11-trip-dispatch.md#driver-app)).

The Integration console (`integration-console-web` on the Aspire dashboard) is where the Integration operator follows messages through the integration layer ([docs/operations/integration-console.md](docs/operations/integration-console.md)). So far it signs in and searches Message trails: one row per trail with its flows, first and last seen, worst outcome and business keys, never a body. A result opens its Message trail: its hops in time order, each with flow, time, duration, outcome and failure code, fan-out indented under the hop that caused it, and its business keys, each a search of its own. A Logic App hop opens its run, read live from the Logic Apps management API: its steps with status, duration and error, and a step, when you open it, with its input and output bodies in full, unless the step uses secure inputs or outputs. A run past run history's retention says its body is no longer kept. It never resubmits a run. It has no database. Locally there is no Easy Auth in front of it, so the AppHost signs you in as a local operator holding both of its app roles (`LocalOperator` settings); it refuses those settings outside Development. Locally it searches what the local apps traced, through the Aspire dashboard's telemetry API, so a booking made in the local Partner portal is found by its Transport Order number or correlation ID a few seconds later ([ADR 0027](docs/adr/0027-locally-the-integration-console-searches-the-aspire-dashboards-telemetry.md)). It holds only the current run. It reads a deployed estate instead, as you, with your Azure CLI or IDE sign-in, once you give the AppHost that estate's workspace ID and retention as user secrets (`dotnet user-secrets set Parameters:estate-log-analytics-workspace-id <AZURE_ESTATE_LOG_ANALYTICS_WORKSPACE_ID>` and `Parameters:estate-integration-retention-days`, both in `azd env get-values`), and you hold Log Analytics Reader on the workspace. Logic Apps exist only in Azure, so a run opens only once you also set `Parameters:estate-resource-group-id` (`AZURE_ESTATE_RESOURCE_GROUP_ID`) and hold Logic Apps Standard Reader on the Logic App, as the estate grants the console's identity. Its UI tests run it alone on a test host with every port faked (`ConsoleWebHost`), and sign in by sending the header Easy Auth sends.

The Simulator (`simulator-web` on the Aspire dashboard) feeds the estate with representative orders at a chosen volume ([docs/operations/simulator.md](docs/operations/simulator.md)). It books for the Shippers, has the Planner assign and release, and has the Carriers answer, track and deliver, with a share for each step of the funnel: choose a Preset or set the numbers, preview the plan, which a seed makes reproducible, then start a run. Each booking is sent to the Norvia Partner API as its Shipper's Persona, a good one or a bad one (no Lane, a repeated or conflicting reference, invalid content), as fast as the estate accepts or paced over a window. A live log names the correlation ID Norvia answered each with and links it to the Message trail in the Integration console. One run is active at a time, and the caps (`Simulator:MaxOrdersPerRun`, `Simulator:MaxConcurrentRequests`) refuse a plan over the limit. It has a database of its own, is off unless `Simulator:Enabled` is set, and locally signs you in as a local operator; in Azure Easy Auth signs the presenter in and the Simulator reaches the estate as its own identity ([ADR 0039](docs/adr/0039-the-simulator-books-only-through-the-estates-real-doors.md), [ADR 0042](docs/adr/0042-the-simulator-signs-in-with-easy-auth-reaches-the-estate-as-its-own-identity-and-plays-the-personas-and-drivers-through-entra-client-apps.md)).

The TMS database's migrations are a deployment step, not something the TMS does when it starts ([coding guidelines §5](docs/coding-guidelines.md#5-persistence-ef-core-with-ardalis-repositories-and-specifications)). `Norvia.Tms.Migrations` applies them and exits; the TMS API and UI wait for it.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs the pull request gates of the coding guidelines on every PR and on `main`: a warning-free build, `dotnet format`, the vulnerable-package check, unit and architecture tests with the coverage gate, and the integration tests.

## Deploying to Azure

Needs the [Azure Developer CLI](https://aka.ms/azd) and the Azure CLI, both signed in to the same tenant as a user who may create resources in the subscription and app registrations in Entra ID, plus `jq` and `zip`.

```bash
azd env new <environment> --subscription <subscription-id> --location <region>
AZD_UP_CONCURRENCY=1 azd up                  # one image at a time (see below)
infra/smoke-test-intake.sh                   # after a deployment: checks intake end to end on the deployed TMS
infra/smoke-test-partner-api.sh              # and the demo smoke run: books through API Management as each Persona
# after booking as Brouwer Dranken in the Partner portal, follows the booking's Message trail:
infra/smoke-test-integration-console.sh <Transport Order number> [<correlation ID>]
# after booking another Shipment to Van Dijk Transport, stops the TMS, dead-letters a POD and has you resubmit it, then discard another:
infra/smoke-test-integration-console-dead-letters.sh <Transport Order number>
# after booking Rotterdam to Antwerp and to Düsseldorf as Brouwer Dranken, checks their Rating:
infra/smoke-test-rating.sh <Antwerp's Transport Order number> <Düsseldorf's Transport Order number>
# after assigning, reassigning and releasing that booking's Shipment as the Planner in the TMS UI, checks planning:
infra/smoke-test-transport-planning.sh <Transport Order number>
# after releasing a Shipment to a Carrier set to Auto-reject, releasing it again to Van Dijk Transport and confirming it in the Partner portal, checks Carrier booking:
infra/smoke-test-carrier-booking.sh <Transport Order number>
# after tracking that Shipment as Van Dijk Transport, checks Shipment tracking, the dead-letter queue and a resubmit:
infra/smoke-test-shipment-tracking.sh <Transport Order number>
# after booking another Shipment the same way, delivers it and checks Proof of delivery, the claim check and its dead-letter queue:
infra/smoke-test-proof-of-delivery.sh <Transport Order number>
# finds the seeded Over capacity day; after booking one more Transport Order for it, assigning it to Own fleet and reassigning it to Kessler Spedition, checks that:
infra/smoke-test-over-capacity-day.sh [<Transport Order number>]
# builds, dispatches and amends a Trip, then dispatches one with the presenter panel's "Driver app unavailable" fault switched on, and checks Trip dispatch:
infra/smoke-test-trip-dispatch.sh <scenario 1 Trip number> <scenario 2 Trip number>
# the seeded Trip of the day: the Driver starts it, collects, delivers, fails one and ends it; checks Trip execution, the order of the reports and the path in Application Insights:
infra/smoke-test-trip-execution.sh <Trip number>
```

azd asks for the AppHost's parameters, which are the estate's outputs, before it runs the preprovision hook. So `azd up` also runs the estate hook as a preup hook, before anything else, and the preprovision run then sees the estate is already deployed. The hook needs the environment's subscription and region, so create the environment with both, as above. If azd still asks for an `estate_*` parameter, don't type in a value: they are the names and IDs the estate creates. Stop, run `azd hooks run preprovision`, and start `azd up` again.

azd (1.33 and 1.34 at least) builds the AppHost's container images in parallel, and the builds share the .NET SDK's local cache of base-image layers. Two of them can then collide on the same cached layer (`CONTAINER1013 … being used by another process`), and azd cancels the rest. `AZD_UP_CONCURRENCY=1`, or `AZD_DEPLOY_CONCURRENCY=1` for `azd deploy`, builds one image at a time. azd reads both from the shell, not from the azd environment.

`azd up` runs in three steps ([ADR 0004](docs/adr/0004-bicep-owns-the-estate-aspire-owns-the-apps.md)):

1. The estate hook ([infra/provision-estate.sh](infra/provision-estate.sh)), run before `azd up` and before `azd provision`, deploys the estate, [infra/estate.bicep](infra/estate.bicep), into `rg-<environment>`. That covers the Service Bus namespace with the `transport-order-events` topic, Log Analytics and Application Insights, the TMS API's app registration with its intake role, the intake Logic App: a Logic Apps Standard app on a Workflow Standard plan, with its storage account and a Key Vault, and API Management with the Norvia Partner API ([infra/estate/partner-api.bicep](infra/estate/partner-api.bicep)). It also registers the demo UIs, the TMS UI and the Partner portal, in Entra, with only the presenter assigned, and the Integration console with its app roles `IntegrationConsole.Read` and `IntegrationConsole.Resubmit`, both assigned to the presenter, and its managed identity. The Logic App calls the TMS as the intake Logic App's managed identity, the one that holds that role, and reaches its own storage and Key Vault with a second identity that holds nothing else. Its trigger accepts only API Management's identity (Easy Auth). In Entra the estate registers the Norvia Partner API with its `TransportOrders.Submit` role, and one client app per Persona in the seed file, each trusting the Partner portal's managed identity instead of holding a secret; Shipper Personas get the role. Each Persona's subscription key is kept in a Key Vault that only the Partner portal's identity may read. API Management is on the Developer tier, whose first deployment takes about 45 minutes. The hook stores the estate's outputs in the azd environment as `AZURE_ESTATE_*`.
2. azd provisions and deploys the apps from the AppHost into the same resource group: the Container Apps environment, the TMS API (reachable from outside the environment), the TMS UI and the Partner portal (both reachable from the presenter's browser, behind an Entra sign-in; see below), the Integration console (reachable from the operators' browsers, behind its own Entra sign-in and running as the estate's console identity), the migrations as Container Apps jobs, and Azure SQL serverless on the free offer, with a database each for the TMS and the Partner portal. The Partner portal runs as the estate's Partner portal identity, gets each Persona's token from Entra through the Persona's federated credential, and books through API Management. In Azure the AppHost references the estate's Service Bus, workspace and Application Insights instead of creating its own. The TMS trusts only Entra tokens for its app registration, and only the intake Logic App's identity may submit. Its queries also need such a token until API Management's Shipper tracking role arrives (P8); Entra issues one only to a principal holding one of the TMS's roles.
3. The postdeploy hook runs the TMS's and the Partner portal's migrations jobs ([infra/migrate.sh](infra/migrate.sh)) and fails the deployment if either fails. In Azure nothing makes the TMS wait for it, so on a first deployment the TMS logs failed outbox cycles until the schema exists. It then deploys the intake Logic App's workflow and local functions ([infra/deploy-intake-logic-app.sh](infra/deploy-intake-logic-app.sh)) and gives it the TMS's address, which exists only once Aspire has deployed the TMS. The address is kept in the azd environment as `ESTATE_TMS_BASE_URL`, so deploying the estate again keeps it. Last, it gives the demo UIs' and the Integration console's app registrations their sign-in callbacks ([infra/register-sign-in-callbacks.sh](infra/register-sign-in-callbacks.sh)) and prints the address of each UI.

The presenter, the user who ran `azd up`, opens the TMS UI and the Partner portal side by side from their own browser at the addresses the postdeploy hook prints, or at their Container Apps URLs in the portal (`tms-web` and `partner-portal-web`). Container Apps' built-in authentication asks them to sign in with Entra once per browser session; after that the Role switcher and the Persona switcher work as they do locally. Entra admits only users assigned to the estate's *Norvia demo UIs* app registration, which is the presenter alone; assign anyone else who presents the `DemoUis.Use` role in Entra ID. The gate holds no client secret ([ADR 0024](docs/adr/0024-the-demo-uis-are-public-behind-an-entra-gate-for-the-presenter.md)). Locally there is no sign-in.

The presenter also opens the Integration console (`integration-console-web`), where they play the Integration operator. Easy Auth signs them in to the console's own app registration, *Norvia Integration console*, and the console checks that they hold `IntegrationConsole.Read`; anyone without it is refused ([ADR 0026](docs/adr/0026-the-integration-console-signs-operators-in-with-easy-auth-and-checks-their-app-role.md)). The console reads the estate as its own managed identity, never as the operator.

The demo smoke run ([infra/smoke-test-partner-api.sh](infra/smoke-test-partner-api.sh)) is what a presenter repeats after a deployment. It books through API Management as Brouwer Dranken and as Van Dijk Transport, tries a missing or wrong key and token, and follows the accepted and the refused bookings by correlation ID to the Logic App run, the Transport Order, the event and Application Insights. A Persona's token can be had only as the Partner portal's identity, so the Personas' calls run from a throwaway Container Apps job as it. It prints `PASS` or `FAIL` per check.

The presenter then follows a booking through the Integration console ([Presenter smoke run](docs/operations/integration-console.md#presenter-smoke-run)): book as Brouwer Dranken in the Partner portal, and run [infra/smoke-test-integration-console.sh](infra/smoke-test-integration-console.sh) with the Transport Order number it answered with. The script checks that the console's sources hold the booking's Message trail, found by that number and by its correlation ID, with the API Management call, the intake Logic App run and the TMS call, and that the run's steps open with their bodies. It prints the console's pages to open on screen, and never a body.

The presenter checks Rating the same way ([Presenter smoke run](docs/processes/tms/p2-rating.md#presenter-smoke-run)): book as Brouwer Dranken from Rotterdam to Antwerp and to Düsseldorf, and run [infra/smoke-test-rating.sh](infra/smoke-test-rating.sh) with both Transport Order numbers. It reads the TMS as the intake identity from a throwaway Container Apps job, and checks that the Antwerp order is Rated with a Freight Charge, that the Düsseldorf order is Rating failed with `NoMatchingLane` and in the rating exceptions, that both are still waiting for planning, and that each order's intake and rating are on one Message trail. It prints the TMS UI's and the Integration console's pages to open on screen.

The presenter then checks Transport planning ([Presenter smoke run](docs/processes/tms/p3-transport-planning.md#presenter-smoke-run)): as the Planner in the TMS UI, assign the Düsseldorf booking to Van Dijk Transport, reassign it to Kessler Spedition and release it, then run [infra/smoke-test-transport-planning.sh](infra/smoke-test-transport-planning.sh) with its Transport Order number. It reads the TMS as the intake identity from a throwaway Container Apps job, and checks that the Transport Order is Planned with its Shipment, that the Shipment is Released and carried by Kessler Spedition with Van Dijk Transport in its history of assignments, that it has left both of the Planner's lists, and that the assignment, the reassignment and the release each published its event on a Message trail of its own, found by the Transport Order number.

The presenter then checks Carrier booking ([Presenter smoke run](docs/processes/tms/p4-carrier-booking.md#presenter-smoke-run)): set Kessler Spedition to Auto-reject in the Partner portal, release the Düsseldorf booking's Shipment to it as the Planner in the TMS UI, release it again to Van Dijk Transport once it is back in Shipments to release, confirm it as Van Dijk Transport in the Partner portal, and run [infra/smoke-test-carrier-booking.sh](infra/smoke-test-carrier-booking.sh) with its Transport Order number. It reads the TMS as the intake identity from a throwaway Container Apps job, and checks that the Shipment is Booked and carried by Van Dijk Transport, that its two Carrier bookings are Kessler Spedition's Rejected and Van Dijk Transport's Confirmed, each reported sent, and that each booking's release and each answer ran on Message trails found by the Carrier booking numbers, publishing `ShipmentReleased`, `CarrierBookingRejected` and `CarrierBookingConfirmed`.

The presenter then checks Shipment tracking ([Presenter smoke run](docs/processes/tms/p5-shipment-tracking.md#presenter-smoke-run)): with the Shipment of that booking Booked and carried by Van Dijk Transport, run [infra/smoke-test-shipment-tracking.sh](infra/smoke-test-shipment-tracking.sh) with its Transport Order number. It posts `PU`, `DEP` and `POD` as Van Dijk Transport through API Management from a throwaway Container Apps job, and checks that each returns `202 Accepted`, that the Shipment moves through Collected, In transit and Delivered in the Planner's list and leaves it, that a Tracking event for an unknown reference is dead-lettered with `ShipmentNotFound`, and that each call is in Application Insights by correlation ID. It then points the Carrier-tracking Logic App away from the TMS, checks that a `POD` is dead-lettered with `MaxDeliveryCountExceeded`, restores it, and waits for the presenter to resubmit the message from the Integration console, which it checks the TMS recorded.

The presenter then checks Proof of delivery ([Presenter smoke run](docs/processes/tms/p6-proof-of-delivery.md#presenter-smoke-run)): with a second Shipment Booked and carried by Van Dijk Transport, run [infra/smoke-test-proof-of-delivery.sh](infra/smoke-test-proof-of-delivery.sh) with its Transport Order number. It delivers the Shipment as Van Dijk Transport through API Management, from a throwaway Container Apps job, and checks that it is in the Planner's *Delivered without Proof of delivery*. It sends a Proof of delivery with the sample CMR, and checks that it returns `202 Accepted`, that the Shipment leaves the list and its timeline holds the Proof of delivery with its file, and that its blob is gone from the inbound container. It checks that one for an unknown reference is dead-lettered with `ShipmentNotFound` and its blob is still there, that a body over 25 MB is refused with `413`, and that each call is in Application Insights by correlation ID.

The presenter finally checks the Over capacity day of Fleet capacity planning ([Presenter smoke run](docs/processes/tms/p10-fleet-capacity-planning.md#presenter-smoke-run)): run [infra/smoke-test-over-capacity-day.sh](infra/smoke-test-over-capacity-day.sh) without arguments to find the day the TMS seeded Over capacity, book one more Transport Order for it as Brouwer Dranken, assign it to Own fleet as the Planner in the TMS UI to see the Over capacity warning, reassign it to Kessler Spedition, and run the script again with its Transport Order number. It reads the TMS as the intake identity from a throwaway Container Apps job, and checks that the day is Over capacity, that the Shipment is carried by Kessler Spedition with Own fleet first in its history of assignments, and that the assignment and the reassignment each ran on a Message trail of their own.

The presenter finally checks Trip dispatch ([Presenter smoke run](docs/processes/tms/p11-trip-dispatch.md#presenter-smoke-run)): build a Trip from the demo's Shipments as the Planner, see `PayloadExceeded`, dispatch it, see it in the Driver app and take a Shipment off to see version 2; then switch the Partner portal's presenter panel to "Driver app unavailable", dispatch another Trip, see Not delivered and the failed Logic App run, switch it off and send again. Run [infra/smoke-test-trip-dispatch.sh](infra/smoke-test-trip-dispatch.sh) with the two Trip numbers; it stops at each step the presenter does and checks the TMS, the Driver app and Application Insights.

The presenter finally runs the Trip execution demo ([Presenter smoke run](docs/processes/tms/p12-trip-execution.md#presenter-smoke-run)) on the Trip the TMS seeded Dispatched for today: as the Driver in the Driver app, start it, collect the three Shipments, deliver the first with a signature and a photo, fail the second, deliver the third with reservations and end the Trip. Run [infra/smoke-test-trip-execution.sh](infra/smoke-test-trip-execution.sh) with the Trip number; it checks the Trip, the Shipments, the Exceptions and the Re-delivery in the TMS, that the Driver's reports were processed in order through the session, and that the path is in Application Insights by correlation ID.

The presenter last runs a small simulation ([Presenter smoke run in Azure](docs/operations/simulator.md#presenter-smoke-run-in-azure)): sign in to the Simulator, start *Quiet Monday* with seed 349, and run [infra/smoke-test-simulator.sh](infra/smoke-test-simulator.sh) with the run's number. It checks that the Simulator is up behind Easy Auth, that the run's Transport Orders, Shipments and a Trip are in the TMS, and that a booking and a Planner action are in Application Insights by correlation ID.

The intake smoke test runs the intake identity's calls from a throwaway Container Apps job, and sees the event through a Service Bus subscription of its own that it removes afterwards. It needs the rights of whoever ran `azd up`: the estate grants that user Azure Service Bus Data Receiver on the namespace.

The applications hold no secrets. The TMS reaches SQL and Service Bus with its managed identity, and Service Bus accepts no keys. The intake Logic App reaches its storage and the TMS with managed identities too. Only its content share, which Logic Apps Standard still reaches with a storage key, needs one: the estate puts that connection string in Key Vault, and the app reads it through a Key Vault reference. The Application Insights connection string only says where telemetry goes. Retention of Application Insights, Log Analytics and the Logic App's run history is the estate parameter `integrationRetentionDays`, 90 days by default (run history keeps 365 days at most). To change it, set it in [infra/estate.bicepparam](infra/estate.bicepparam).

`azd down --purge` removes the resource group. The app registrations are not in it; delete the ones ending in *(&lt;environment&gt;)* in Entra ID yourself: *Norvia TMS API*, *Norvia Partner API*, *Norvia intake Logic App trigger*, *Norvia demo UIs*, *Norvia Integration console* and each *Norvia Persona*.
